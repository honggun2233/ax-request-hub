# PART 1. 발의서 (Phase 0)

## 제목

AI 과제 개발 표준의 시스템 강제화 — 문서로만 존재하는 표준을 실제 게이트로 전환

## 배경 (왜 지금)

AX Hub의 목적은 **사내 AI 사용의 표준화**다. "AI를 쓰고 싶다"는 개별 요청을 공통 기준(신청→심사→표준검증→배포)으로 필터링해서, 표준을 통과한 것만 상용화까지 보내는 것이 이 시스템의 존재 이유다.

그런데 실제 코드를 전수 검증한 결과, 그 표준이 **문서로만 존재하고 시스템이 강제하지 않는 상태**임이 확인됐다.

| 확인 사항 | 실태 |
|---|---|
| 개발 표준 문서 | AI-STD-2026-006(v1.3) 존재. Phase1 PoC → Phase2 Gate검토 → Phase3 배포, 내용도 구체적 |
| 검증 로직 | `checkTechStandards()` 6항목 체크 구현돼 있음 |
| 입력 경로 | **없음** — 실제 등록 화면(`/projects/new`)이 `techHas*` 필드를 다루지 않음 |
| 검토·제언 화면 | **전부 고아 코드** — `ProjectForm`(`/submit` 미연결), `gate2-checklist`(import 0건), `ScoreCard`(import 0건) |
| GATE 전환 강제 | **없음** — GATE1→GATE2 전환 로직에 `techStandardsPassed` 체크 자체가 없음 |

즉 표준 문서도 있고 검증 함수도 있는데, **둘을 잇는 배선이 전부 끊겨 있어** 실질적으로 아무것도 걸러지지 않는다.

더 심각한 구조적 문제가 검증 과정에서 추가로 드러났다:

- **정식 승인 경로가 작동하지 않음**: 위원회 상용전환 승인(`council/agenda/decide`)은 `prodStatus`만 갱신하고 `lifecycleStage`는 건드리지 않는데, Policy Gateway는 `lifecycleStage`만 참조한다. 정상 승인을 받아도 실행 시점에 계속 차단된다.
- **우회 경로만 작동함**: 전체 코드베이스에서 `lifecycleStage='ACTIVE'`를 세팅하는 곳은 seed를 제외하면 `PATCH /api/registry`의 `operatorTrustScore` 분기 단 한 곳이며, 이 경로는 5요건 검증(`checkProdEligibility`)을 전혀 거치지 않는다.

**표준화 관점에서 이것이 의미하는 바**: 정식 경로가 막혀 있으니 비표준 우회 경로가 그 공백을 메웠고, 결과적으로 **검증을 건너뛰는 경로가 사실상 유일한 표준이 되어버린** 상태다. 표준화 작업에서 가장 경계해야 할 실패 양상이다.

## 가설

배선을 잇고(트랙 A) 게이트를 강제하면(트랙 B), AX Hub는 "AI 사용 신청을 기록하는 시스템"에서 **"표준 미달을 실제로 걸러내는 시스템"**으로 전환된다. 신규 기능 개발보다 기존 자산을 연결하는 비중이 크므로 투입 대비 효과가 높다.

## 범위 추정

- 트랙 A(배선): 1~2일 — 기존 컴포넌트 연결이 대부분, 신규 로직 없음
- 트랙 B(게이트화): B-0/B-1/B-1b/B-3 각 반나절, B-2(인수신청 신규개발) 별도 2~3일
- 스키마 변경: 없음
- 별도 트랙: 거버넌스 문서 개정(결재선), 소급 방침 결정(PO 판단)

## 분류

🏢 회사 프로젝트 / AX Request Hub / 운영 중 시스템 개선

# PART 2. 기능 기획서 (Phase 1)

## 기능명

AI 개발 표준 필터링 게이트 (Dev-Standard Filtering Gate)

## 배경 (왜 지금)

위 발의서 참조. 요약하면 — 표준 문서·검증 로직은 있으나 입력 경로·강제 게이트가 없어 실질적 필터링이 0인 상태이며, 동시에 정식 승인 경로가 작동하지 않아 비표준 우회 경로가 유일한 통로가 되어 있음.

## 목표 (성공 기준)

| # | 성공 기준 | 측정 방법 |
|---|---|---|
| 1 | 신청자가 기술표준 6항목을 실제로 입력할 수 있다 | `/projects/new`에서 입력 후 DB에 `techHas*` 값 저장 확인 |
| 2 | 표준 미달 시 신청자가 사유를 확인할 수 있다 | `/me/projects`에서 미달 항목 목록 노출 |
| 3 | 표준 미달 건은 GATE2로 전환되지 않는다 | GATE1→GATE2 PATCH 시 422 반환 |
| 4 | 위원회 정식 승인 건이 실제로 실행 가능해진다 | 승인 후 `lifecycleStage='ACTIVE'` + Policy Gateway ALLOW 확인 |
| 5 | 검증 우회 경로가 제거된다 | ACTIVE 직행 시도 시 `checkProdEligibility` 422 |
| 6 | 두 활성화 경로가 동일하게 동작한다 | 위원회 경로·직행 경로 모두 `gate2Passed`·Agent 연결 등 부수효과 일치 |

## §5. B-4 소급 처리 방침 — **확정 (2026-09-07)**

**결정: 옵션 B(시행일 기준). 소급 재점검 과제 별도 편성 불필요.**

운영 DB 실조회 결과 (전체 에이전트 35개):

| 항목 | 건수 | 비율 |
|---|---|---|
| `syncGap` — 위원회 승인됐으나 Policy Gateway에서 차단 중 | **3건** | 8.6% |
| 옆문 통과 의심 — `lifecycleStage='ACTIVE'` && `techStandardsPassed=false` | **0건** | 0% |

**해석**:
- 옆문 통과 0건 → 검증 없이 상용 운영 중인 에이전트가 실제로 없음. 소급 리스크 없어 옵션 B로 단순 확정
- 동시에 이 숫자는 **B-1b(우회 차단)의 성격을 "구멍 막기"에서 "예방 조치"로 바꿈** → 우선순위 하향
- 반면 syncGap 3건은 **현재 진행 중인 운영 장애** — 정식 절차를 다 통과한 에이전트가 사용자에게 열리지 않고 있음 → **B-0 긴급 배포 근거**

**추가 확인**: 당초 "우회 경로가 사실상 유일한 활성화 통로였을 것"으로 추정했으나 옆문 통과 0건으로 **실제 우회 사례는 없었음**이 확인됨. 비표준 관행이 정착하기 전에 발견한 것으로, 표준화 착수 시점으로는 유리함.
