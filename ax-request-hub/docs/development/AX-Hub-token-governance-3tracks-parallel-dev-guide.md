# AX Hub 토큰관리 종합 설계 — 3트랙 구조 + 병렬 개발 가이드

**작성일**: 2026-08-21
**배경**: 거버넌스 관리의 두 축(에이전트 관리·토큰 관리) 중 토큰 관리가 중점 사항으로 재확인됨. 현재 에이전트 관리는 실제 코드가 여러 라운드 돌고 있는 반면, 토큰 관리는 세 트랙 모두 설계는 정교하나 실제 구현은 거의 없는 상태. 이 격차를 메우기 위한 종합 정리와, 에이전트 관리 개발과 병렬 진행하기 위한 가이드.

---

## 1. 현황 진단

| 트랙 | 설계 완성도 | 실제 구현 상태 |
|---|---|---|
| A (엔터프라이즈 계정: Claude/GPT/Gemini) | 높음 | 0% — 벤더 API 키 미발급, 수집 스크립트 없음 |
| B (AX Hub 자체 엔진) | 4차 정정 끝에 확정 | 재작업 필요 — 기존 코드(`ModelProvider`/`costRank`/`selectProvider`)가 잘못된 전제 위에 있음 |
| C (배포 에이전트 런타임) | 있음 | 0% — 서비스토큰 인증(middleware.ts) 미해결로 착수 불가 |

에이전트 관리(Gate1~3, KPI, 데이터 프로비저닝)는 버그는 있지만 실제로 작동하는 코드가 여러 라운드 누적된 반면, 토큰 관리는 세 트랙 다 뼈대만 있고 실행되는 코드가 거의 없다. 토큰 관리가 중점 사항이라면 지금까지의 개발 우선순위가 반대로 되어 있었던 셈.

---

## 2. 왜 세 갈래로 나뉘는가

토큰 관리를 하나의 시스템으로 묶으려던 게 초기 설계의 근본 오류였다. 실제로는 "누가 쓰고, 어디서 실행되고, 돈이 어떻게 나가는지"가 완전히 다른 세 상황이다.

```
A트랙: 직원이 엔터프라이즈 앱에서 직접 씀       (Claude.ai, ChatGPT, Gemini 앱)
B트랙: AX Hub 자신이 심사 업무를 위해 씀        (인테이크 파싱, Gate 심사, KPI 채점)
C트랙: 승인받아 배포된 에이전트가 운영 중 씀    (예: ETF 리밸런싱 봇)
```

---

## 3. A트랙 — 엔터프라이즈 계정 사용량

**흐름**: 직원이 Claude.ai/ChatGPT/Gemini 앱을 직접 사용, AX Hub는 관여하지 않음. 각 벤더의 관리자용 API(Claude Enterprise Analytics API, OpenAI 조직 사용량 API, Google 유사 API)를 일 1회 배치로 조회해 사용량을 당겨온다(Pull).

**Pull 방식인 이유**: AX Hub가 직원의 채팅 세션에 개입할 방법이 없다. 사후 집계를 당겨오는 게 유일한 방법.

**데이터 구조**: 벤더 API는 보통 일 단위 집계까지만 제공. 원본은 일 단위 테이블(`UsageRecordDaily`)에 적재 후 월 단위(`UsageRecord`)로 롤업해 부서별 쿼터 체크에 사용.

**착수 조건**: Claude Enterprise Analytics API 키 발급(Primary Owner 권한 필요) — 이게 A트랙의 유일한 시작점.

**코드 결합도**: 완전히 별도 테이블·별도 흐름. 에이전트 관리 쪽 코드를 전혀 건드리지 않음 — 병렬 진행에 가장 안전한 트랙.

---

## 4. B트랙 — AX Hub 자체 엔진 (심사 업무용)

여러 차례 정정 끝에 확정된 최종 구조:

```
[Gate 심사·인테이크 파싱 등 작업]
      ↓
[온프렘 Qwen] ← 실행하지 않고 "판단만" 함
      "이 작업엔 Claude가 맞다 / GPT가 맞다" 추천
      ↓
[AWS Bedrock 경유로 실제 실행]
      Claude, GPT, (Gemini 또는 Gemma) 중 추천받은 것으로 실제 작업 수행
      ↓
[AX Hub가 그 자리에서 자체 기록(Push)]
```

**Qwen이 실행 안 하는 이유**: Qwen은 AX Hub 자체 인프라라 비용이 거의 없지만 판단력 검증이 덜 됨. 실제 심사 업무(코드리뷰·근거생성)는 품질이 중요하므로 "저비용 감독자(Qwen) + 검증된 실행자(Bedrock 경유 벤더모델)" 구조로 분리.

**기밀등급 제약 해소**: 초기엔 "G3는 Qwen 전용"으로 설계했으나, Bedrock은 AWS 계정 경계 내 처리라 데이터가 회사 밖으로 나가지 않는다. G1~G3 전부 Bedrock 경유로 처리 가능 — 이 결론에 도달하기까지 라우팅 설계를 4차례 갈아엎었다.

**토큰 기록**: Bedrock 호출 직후 AX Hub가 자체 기록(Push). 벤더 관리자 API에 의존하지 않는 이유는, Bedrock 사용료가 AWS 청구서에 잡히지 벤더사 콘솔에 안 잡히기 때문(A트랙과 다른 지점).

**주의**: Jarvis가 이미 구현한 `ModelProvider.costRank/qualityRank`, `selectProvider()`의 비용·품질 비교 로직은 "Qwen이 클라우드와 경쟁한다"는 잘못된 전제 위에 있어 폐기 대상. `GatewayCallLog`(이벤트 단위 토큰 기록)는 목적 자체는 유효하므로 유지.

---

## 5. C트랙 — 배포 에이전트 운영 비용

**흐름**: AWS 랜딩존 샌드박스에 배포된 에이전트가 스스로 AI를 호출하고, 자기 사용량을 AX Hub에 직접 보고(Push).

**Push를 쓰는 이유**: B트랙과 동일 — 어떤 인프라·벤더로 바뀌든 AX Hub 자체 기록 방식은 흔들리지 않는다. 벤더나 AWS 콘솔 사후 수집(Pull)에 의존하면, 인프라가 바뀔 때마다 수집 로직을 다시 만들어야 한다(과거 `collect-llm-usage.ts` 폐기 논쟁에서 얻은 교훈).

**전제조건(현재 블로커)**: 에이전트가 자기 사용량을 보고하려면 "이 요청이 정말 그 에이전트가 보낸 게 맞다"를 확인할 서비스 토큰 인증이 필요. `middleware.ts`가 현재 사람의 로그인 세션만 다루고 있어, 에이전트 같은 비인간 호출자를 위한 인증 경로가 없음.

---

## 6. 통합 조회 (후속, 지금 착수 안 함)

경영진이 "이번 달 AI 비용 총액"을 보려면 A·B·C 세 테이블을 합산 조회하는 대시보드가 필요하다. 각 트랙의 수집 방식은 다르지만 최종적으로 하나의 숫자(A+B+C)로 합쳐져야 의미가 있다. **이 통합 대시보드는 세 트랙이 각자 자리 잡은 뒤 착수** — 지금은 재료(각 트랙의 실제 데이터)가 없어 대시보드부터 만들 수 없다.

---

## 7. 병렬 개발 가이드 — 에이전트 관리 개발과 어떻게 병행하는가

| 항목 | 병렬 가능 여부 | 비고 |
|---|---|---|
| 에이전트 관리 개발 계속 | 가능 — 그대로 진행 | 토큰관리와 스키마 결합 거의 없음 |
| A트랙 설계·착수 | 가능 — 지금 바로 시작 | 코드 결합 없음, 병렬 진행에 가장 안전 |
| B트랙 재설계 반영 | 조건부 | §7-1 참고 |
| middleware.ts 인증 통합 | 병렬 아닌 즉시 처리 권장 | §7-2 참고 |

### 7-1. 잘못 지어진 B트랙 코드 — 동결 처리

`ModelProvider`/`costRank`/`selectProvider()` 등 폐기 대상 코드에 더 이상 기능을 얹지 않도록 Jarvis에게 "재설계 대기 중, 추가 확장 금지"를 명시적으로 전달. 삭제는 재설계 반영 시점에 한 번에 처리해도 되지만, 그 사이 이 코드 위에 새 기능이 쌓이면 안 됨.

### 7-2. Gate1~3 AI 호출 라우트 — 리팩터링 순서 조율

`intake/parse`, `evaluate`, `score` 라우트는 B트랙 재설계가 반영되면 AI 호출 방식이 바뀐다. 에이전트 관리 개발이 이 특정 파일들을 크게 리팩터링할 계획이 있다면, B트랙 재설계 머지 이후로 순서를 미룰 것. 두 작업이 같은 파일에서 동시에 바뀌면 충돌한다.

### 7-3. middleware.ts는 병렬이 아니라 지금 같이 처리

에이전트 관리(KPI 인증 불일치)와 토큰관리 C트랙(서비스토큰) 양쪽 다 이 위에 서 있다. 어느 트랙이 먼저 끝나든 결국 여기서 막히므로, 미룰 이유가 없다.

## 8. 최종 순서

```
지금 시작:
  - 에이전트 관리 개발 (계속)
  - A트랙 설계·착수 (Analytics API 키 발급부터)
  - middleware.ts 인증 통합

동결(건드리지 않기):
  - ModelProvider/costRank 등 잘못된 B트랙 코드

순서 조율 필요:
  - B트랙 재설계 머지 (intake/evaluate/score 라우트 리팩터링 시점과 조율)

나중:
  - C트랙 착수 (middleware.ts 완료 후)
  - A·B·C 통합 조회 대시보드 (세 트랙 각각 자리잡은 후)
```
