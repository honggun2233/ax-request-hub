# AX Hub 사이드바 — 용어 통일 + 개념 중복 정리안

**작성일**: 2026-08-21
**배경**: 회의 결정사항 #1("AI 활용 신청"→"에이전트 등록 신청" 명칭 통일)이 사이드바 라벨에 아직 반영 안 됨 + AX_TEAM이 보는 화면에 비슷한 개념이 여러 섹션에 중복 노출

---

## 1. 문제 진단

### 문제A — "AI"와 "에이전트"가 뒤섞여 쓰임
지금 사이드바 라벨: "AI 활용 신청", "AI 직접 활용", "AI 파이프라인", "활용 현황", "AI 위원회" — 전부 "AI"라는 같은 단어를 쓰지만 가리키는 대상이 다 다릅니다.

| 라벨 | 실제로 가리키는 것 |
|---|---|
| AI 활용 신청 | 에이전트를 새로 등록하는 신청 |
| AI 직접 활용 (/me/ai) | 에이전트가 아니라 개인이 Claude/GPT/Gemini를 그냥 채팅하는 것 |
| AI 파이프라인 | 에이전트 레지스트리·KPI관리·영향도분석 (에이전트 운영 전반) |
| AI 위원회 | 에이전트 등록 심의 위원회 |

**"에이전트"가 맞는 곳(3개)과 "AI"가 맞는 곳(1개, /me/ai)이 전부 "AI"로 통일돼 있어서, 정작 구분해야 할 지점에서 구분이 안 됩니다.**

### 문제B — 같은 기능이 이름만 다르게 두 섹션에 중복 노출
| 중복 항목 | 위치1 | 위치2 |
|---|---|---|
| 도구 배정 | 팀 관리(DEPT_HEAD) | 플랫폼 관리(AX_TEAM) |
| 데이터 승인/심사 | 심사&위원회(AX_TEAM) "데이터 승인" | 데이터 거버넌스(DATA_PLATFORM) "데이터 신청 심사" |

둘 다 스코프(팀 단위 vs 전사 단위, 실행 vs 조회)가 다를 가능성이 높은데 라벨이 똑같아서 개발자도 헷갈리고, 실제로 같은 화면인지 다른 화면인지 코드를 봐야 압니다.

### 문제C — AX_TEAM 한 사람이 보는 화면에 유사 개념 3개 섹션 분산
AX_TEAM 역할은 "AI 파이프라인", "심사&위원회", "플랫폼 관리" **3개 섹션을 동시에** 봅니다. 전부 "에이전트를 관리한다"는 큰 틀 안에 있는데 섹션이 나뉘어 있어 정확히 지금 지적하신 "비슷한 개념이 장황하게 펼쳐진" 상태를 만듭니다.

## 2. 이름 변경 원칙

1. **에이전트와 직접 관련된 모든 것 → "에이전트"로 통일**: 신청·심사·운영·위원회·레지스트리 전부
2. **"AI"는 `/me/ai` 한 곳에만 남긴다**: 이게 유일하게 에이전트가 아니라 "개인이 AI를 직접 쓰는" 기능이라 구분점이 됩니다
3. **스코프가 다른 동명 기능은 스코프를 라벨에 명시**: "팀 도구 배정" vs "전사 도구 배정 정책"처럼

---

## 3. 라벨 변경안

| 기존 라벨 | 변경 후 | 이유 |
|---|---|---|
| AI 활용 신청 | **에이전트 등록 신청** | 회의 결정사항 #1 그대로 반영 |
| AI 직접 활용 | AI 직접 활용 (유지) | 유일하게 "AI"가 맞는 지점 |
| AI 파이프라인 | **에이전트 운영** | 안에 레지스트리·KPI·영향도분석이 있어 "파이프라인"보다 "운영"이 실제 내용과 맞음 |
| 활용 현황 | **에이전트 활용 현황** | 무엇의 활용 현황인지 명시 |
| AI 위원회 | **에이전트 심의위원회** | 신청서를 심의하는 대상이 에이전트임을 명시 |
| 심사 관리 | **에이전트 심사 관리** | "심사"만으론 데이터 심사와 혼동 가능 |
| (팀 관리) 도구 배정 | **팀 도구 배정** | 스코프 명시 |
| (플랫폼 관리) 도구 배정 | **전사 도구 배정 정책** | 스코프 명시, 정책 수립 성격임을 명시 |
| (심사&위원회) 데이터 승인 | **데이터 요청 현황** (조회 전용이면) 또는 제거 | DATA_PLATFORM 쪽과 기능 중복 여부 확인 후 결정 |
| 데이터 신청 심사 | 데이터 신청 심사 (유지) | 실제 승인 권한이 있는 DATA_PLATFORM 쪽 라벨은 그대로 |

## 4. 섹션 통합안 — AX_TEAM 3섹션 → 2섹션

지금: **AI 파이프라인 / 심사&위원회 / 플랫폼 관리** (3개, 다 AX_TEAM 대상)

```
통합 후:

[에이전트 거버넌스]  ← 에이전트의 생애주기 전체를 여기 하나로
  - 에이전트 심사 관리 (Gate1~3)
  - 이의제기
  - 에이전트 심의위원회
  - 에이전트 레지스트리
  - 에이전트 운영·KPI 관리
  - 영향도 분석
  - 에이전트 활용 현황

[플랫폼 운영]  ← 에이전트가 아니라 시스템/조직을 관리하는 것
  - 직원·교육
  - 토큰·쿼터
  - 전사 도구 배정 정책
  - 감사 로그
  - 스킬 관리
  - 규정·지침
```

**분류 기준**: "에이전트 자체에 대한 판단·이력·운영"이냐 "에이전트 밖의 조직·인프라 설정"이냐로 나눴습니다. 지금처럼 "파이프라인/심사/플랫폼"이라는 프로세스 단계 기준보다, "무엇을 다루는가" 기준이 실제 업무 흐름(에이전트 하나를 등록부터 폐기까지 계속 추적)과 더 잘 맞습니다.

## 5. 최종 사이드바 구조 (전체, 역할별 노출)

| 섹션 | 대상 | 메뉴 |
|---|---|---|
| 홈 | 전 직원 | / |
| 에이전트 신청 | 전 직원 | 에이전트 등록 신청, 내 신청 현황, 데이터 신청, 내 데이터 현황 |
| AI 직접 활용 | 전 직원 | AI 채팅 (/me/ai) |
| 내 정보 | 전 직원 | 프로필·교육, 도구&서비스, 규정·문서 |
| 팀 관리 | DEPT_HEAD | 팀 도구 배정 |
| 경영 현황 | EXECUTIVE | 경영 대시보드 |
| 데이터 거버넌스 | DATA_PLATFORM | 데이터 신청 심사, 카탈로그 관리 |
| **에이전트 거버넌스** | AX_TEAM | (§4 통합 내용 전체) |

## 6. 확인 필요 — 개발 착수 전에

**"데이터 승인"(AX_TEAM 심사&위원회 안)과 "데이터 신청 심사"(DATA_PLATFORM)가 같은 API를 부르는 같은 화면인지, 아니면 AX_TEAM은 조회만 하고 실제 승인은 DATA_PLATFORM만 하는 다른 화면인지** 확인이 필요합니다. 같은 기능이면 DATA_PLATFORM 화면 하나로 합치고 AX_TEAM에게도 역할 기반으로 노출 권한만 주는 게 맞고, 다른 기능(조회 vs 승인)이면 라벨을 "데이터 요청 현황(조회)"로 명확히 구분해야 합니다.

같은 방식으로 **"도구 배정"도 팀 관리와 플랫폼 관리에서 실제로 다른 API를 부르는지** 확인해야 §3의 라벨 변경(팀/전사 구분)이 정확해집니다.

## 7. 개발 반영 가이드 (Jarvis 전달용)

```
1. app-sidebar.tsx 라벨 텍스트만 변경 — §3 표 그대로 적용 (기능/API 변경 없음)
2. AX_TEAM 대상 섹션 3개(AI 파이프라인/심사&위원회/플랫폼 관리) → 2개(에이전트 거버넌스/플랫폼 운영)로 재편성
   - 메뉴 항목 자체는 이동만 함, 페이지·API는 변경 없음
3. §6 확인 후:
   - "도구 배정" 중복이 실제 동일 기능이면 컴포넌트 재사용 + 역할별 스코프 필터로 통합
   - "데이터 승인" 중복이 실제 동일 기능이면 AX_TEAM 쪽 항목 제거, DATA_PLATFORM 화면에 조회 권한만 추가
```

이번 작업은 **라벨·섹션 배치 변경이 중심**이라 스키마·API 변경이 필요 없습니다(§6 확인 결과에 따라 도구배정/데이터승인만 예외적으로 컴포넌트 통합이 필요할 수 있음). 이전 릴리즈(v24)의 `agentRegistryId` 자동세팅 이슈와는 별개 작업이라 병행 진행 가능합니다.
