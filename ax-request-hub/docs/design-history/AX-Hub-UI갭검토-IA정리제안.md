## 1. 코드 리뷰 — 두 이전 문서와 교차 대조 결과

### 🔴 Critical — RETIRE_CANDIDATE 자동화가 사실상 죽은 코드

스키마 확인 결과 KPI 추적 경로가 완전히 분리된 두 갈래입니다.

```
갈래1 (레거시): Agent 모델
  → AgentKpiRecord (recordMonth, actualValue, tokenCost...)
  → Agent.kpiLastScore / kpiMissCount / performanceFlag

갈래2 (신규, v23구현 문서): AgentRegistry 모델
  → AgentScore (phase=PRODUCTION, month, achieveRate...)
  → AgentRegistry.retireFlag ← "3개월 연속 60% 미달 자동플래그" 로직이 여기 있음
```

이번 갭 수정에서 `app/admin/agents/page.tsx`의 "KPI 기록" 버튼은 **갈래1**(`POST /api/admin/agents/[id]/kpi-record`)에 연결됐습니다. **갈래2**(`POST /api/registry/[id]/kpi-score` — 자동플래그 로직이 있는 엔드포인트)는 89개 라우트 전수 스캔 표에 없고, item 9에서 `/registry/[id]/kpi-score` **페이지**에 링크만 추가했을 뿐 — 그건 이력을 "보는" 화면이지 새 점수를 "입력하는" 화면이 아닙니다.

**결과**: 관리자가 실제 쓰는 버튼은 옛날 방식(`Agent.performanceFlag`)에 계속 쌓이고, `AgentRegistry.retireFlag` 자동화는 입력이 안 들어오니 영원히 발동하지 않습니다. `flags/route.ts`가 두 모델을 둘 다 조회해서 합치는 이유도 이 분리 때문인데, 이번 갭 수정이 그 분리를 UI 연결로 굳혀버렸습니다.

**조치**: `admin/agents/page.tsx`의 "KPI 기록" 버튼을 `/api/registry/[id]/kpi-score`로 재연결하거나, 두 모델을 FK로 통합(스키마 주석에 "중기적으로 연결 예정"이라 이미 적혀 있음)한 뒤 단일 엔드포인트로 정리해야 합니다.

### 🔴 Critical — 데이터 요청 승인 흐름, 절반만 고쳐짐

item 4에서 스스로 이렇게 적었습니다: "APPROVED/REJECTED → 신규 엔드포인트로 교체, **그 외 전환은 기존 PATCH 유지**." 그런데 그 "기존 PATCH"가 이 문서 자신이 지적한 문제(역할 체크·감사로그 없음) 그 자체입니다. v23구현 문서에 `POST /api/dp/requests/[id]/review`(정식 역할체크+감사로그 포함)가 이미 있는데 UI는 안 씁니다. 승인/반려(끝 단계)만 고치고 그 앞 두 단계는 취약한 상태 그대로입니다.

**조치**: `dp/requests/page.tsx`의 REQUESTED→REVIEWING, →SEC_REVIEW 전환도 `POST /api/dp/requests/[id]/review`로 교체.

### 🟠 확인 필요 — `/me/ai` 페이지가 A/B트랙 경계를 흐림

`anthropic/openai/gemini/onprem` 4개를 노출하는 AX Hub 내부 채팅 UI입니다. 여기서 나는 사용량이 A트랙 벤더 API 수집으로 잡히는지, AX Hub가 직접 기록해서 이 채널만큼은 실시간 데이터를 확보하는지 확인이 필요합니다. 후자라면 벤더 API의 일 단위 한계를 이 채널에서만은 뛰어넘는 셈이라 오히려 긍정적입니다.

### 🟡 Minor — 문서 중복

item 5와 item 8이 "AI 대화 신청" 내용을 거의 그대로 두 번 기록. 기능 문제 아님, 진행기록 정리 문제.

### 확인된 좋은 점
- 89개 API 라우트 전수 대조 방법론 — 이번에 잡은 문제도 이 스캔이 있었기에 드러남
- 아티팩트 삭제: 서버·클라이언트 이중 방어 확인됨

## 2. 정보구조(IA) 정리 제안 — "기능이 나열된 상태"를 역할·의도 기준으로 재편

### 지금 상태의 문제

사이드바가 **기능 단위**(카탈로그, 위원회, KPI, 리터러시, 배분, 토큰...)로 계속 늘어나는 구조입니다. 새 기능이 생길 때마다 사이드바에 항목이 하나씩 추가되는 패턴이라, 쓰는 사람 입장에서 "내가 뭘 하러 왔는지"보다 "이 메뉴가 뭘 하는 메뉴인지"부터 파악해야 합니다.

**구체적 증거**: "AI 대화 신청"이 사이드바에도 별도 링크(`/chat`)로 있고, `/projects/new` 안에도 4번째 탭(CHAT)으로 또 있습니다. 같은 행위(에이전트 신청)에 진입점이 두 개입니다 — 정확히 지금 지적하신 "신청 관련 항목을 하나로 묶어야 한다"는 사례입니다.

### 재편 방향 — 역할과 의도 기준 6개 섹션

| 섹션 | 대상 | 포함 항목 (현재 흩어진 것들) |
|---|---|---|
| **① 에이전트 신청** | 전 직원 | `/projects/new` 하나로 통합 — 폼/파일/프롬프트/대화 4채널은 이 화면 안의 **탭**으로만 존재. 사이드바 `/chat` 별도 링크는 제거하고 `/projects/new`의 CHAT 탭으로 흡수 |
| **② 내 신청 현황** | 전 직원 | 내 프로젝트 상태, `/me/data`(데이터 신청 현황) — "내가 뭘 냈고 지금 어디 있는지"를 한 곳에서 |
| **③ AI 직접 활용** | 전 직원 | `/me/ai` — "에이전트를 만드는" 게 아니라 "그냥 AI를 쓰는" 것이므로 ①과 명확히 분리 |
| **④ 심사·운영** | AX_TEAM | Gate1~3 심사 큐, `/registry`(라이프사이클), `/admin/agents`(KPI·폐기), `/admin/retired`(지식추출), `/council`(위원회) |
| **⑤ 데이터 거버넌스** | DATA_PLATFORM | `/dp/catalog`, `/dp/requests` |
| **⑥ 정책 관리** | AX_TEAM(관리자) | `/admin/tokens`, `/admin/distribution`, `/admin/literacy` — "설정하고 관리하는" 성격이 같은 것끼리 |

경영진 대시보드(`/executive`)는 역할이 명확히 분리되므로 별도 최상위로 유지.

### 판단 기준

새 기능을 추가할 때 "어느 기능 카테고리에 넣을까"가 아니라 **"누가, 무엇을 하러 오는가"**로 먼저 분류하고, 그 다음에 섹션 안 세부 항목으로 넣는 순서를 권합니다. 지금처럼 기능이 생길 때마다 사이드바 최상위에 항목을 추가하면 6개월 뒤엔 다시 지금과 같은 상태가 됩니다.

### 선행 조건

이번에 발견한 KPI 이중화(§1)처럼, **UI를 합치기 전에 뒤에서 데이터가 갈라져 있는 곳부터 먼저 정리**해야 합니다. 화면만 하나로 합쳐놔도 뒤에서 여전히 두 모델에 나뉘어 쌓이면, 사용자는 하나의 화면을 보고 있다고 착각하지만 실제로는 어느 버튼을 눌렀느냐에 따라 결과가 갈라지는 상태가 계속됩니다. 순서는: **① 백엔드 모델 통합(Agent↔AgentRegistry FK 연결) → ② 엔드포인트 단일화 → ③ 프론트 IA 재편**입니다.
