## 2. 이번 수정에서 새로 발견된 문제

### 🔴 Critical — `registryId`가 실제로 언제 채워지는지 확인되지 않음

item 14는 필드를 추가했다고 하고, item 15는 그 필드가 있으면 신규 경로로 분기한다고 합니다. 그런데 **그 필드에 값을 실제로 세팅하는 코드가 이번 목록 어디에도 없습니다.**

스키마에 `registryId String? @unique`를 추가한 것과, `Agent` 생성 시점(아마 Gate3 통과 후 배포 시점)에 이 값을 실제로 채우는 것은 별개 작업입니다. 이게 없으면:
- 기존 `Agent` 레코드는 전부 `null` (백필 계획 언급 없음)
- 신규 `Agent`도 어디선가 명시적으로 안 채우면 계속 `null`
- item 15의 분기 로직은 있으나 마나, 영원히 레거시 경로로만 빠져 **고치려던 버그가 형태만 바뀐 채 재발**

**확인 필요**: `Agent`+`AgentRegistry`를 함께 만드는 지점에서 `registryId`를 세팅하는 코드 존재 여부, 기존 레코드 백필 계획.

### 🟡 Medium — `prisma db push` 운영 관행

마이그레이션 파일을 안 남기는 방식이라 스키마 변경 이력이 추적 안 됩니다. 지금 필드(nullable)는 위험이 낮지만 앞으로 `prisma migrate`로 전환 권장. 급한 건 아님.

### 확인 안 된 채 남은 것
- item 4/13의 "나머지 → 구형 PATCH"가 정확히 어떤 전환인지 미명시. 감사로그 없는 전환이 남아있다면 같은 문제가 일부 잔존.
- `/me/ai` 사용량이 A트랙 어디로 잡히는지 여전히 미확인.

## 3. 근본 질문 — 이게 "진짜" 에이전트 관리 구조인가

**결론: 아직 아닙니다. 버그는 고쳤지만 구조는 통합되지 않았습니다.**

### 문제의 본질

```
Agent(레거시) ←--- registryId(nullable FK) ---→ AgentRegistry(신규)
   ↳ performanceFlag                              ↳ retireFlag
   ↳ AX팀 KPI 관리                                  ↳ 전사 라이프사이클
```

`registryId` 유무로 UI가 분기하는 지금 구조는 **"어느 에이전트가 어느 필드를 갖고 있느냐에 따라 은퇴 판정 로직 자체가 통째로 달라진다"**는 뜻입니다. 같은 회사 안에서 에이전트 A는 "3개월 연속 60% 미달" 규칙으로 판정받고, 에이전트 B는 완전히 다른 레거시 규칙으로 판정받습니다 — 이게 데이터 구조의 우연(언제 만들어졌는지)에 좌우됩니다.

이는 AX Hub 워크플로우 설계 전반에서 유지해 온 원칙("거버넌스 규칙은 하나여야 설명 가능하다")과 정면으로 배치됩니다. 지금 상태로 "완료"로 넘기면, 나중에 "왜 이 에이전트는 은퇴 후보로 안 잡혔는가"라는 질문에 "그 에이전트가 어느 모델에 있었는지에 따라 다릅니다"라고 답하게 됩니다 — 설명 가능하지 않은 상태입니다.

### 두 가지 선택지 (택1 필요)

| 선택지 | 내용 | 트레이드오프 |
|---|---|---|
| **1. 완전 통합** | `Agent`의 KPI/폐기 필드를 `AgentRegistry`로 흡수, `Agent` 모델 단계적 폐기 | 마이그레이션 공수 크지만 근본 해결 |
| **2. 영구 이중 트랙 공식화** | 두 트랙을 유지하되 "어느 트랙을 쓰는지"를 데이터 구조 우연이 아닌 명시적 정책(부서·유형 기준)으로 확정 + 동기화 메커니즘 구축 | 공수는 작지만 복잡도가 영구히 남음 |

**판단**: 1번(완전 통합)을 권합니다. `Agent`와 `AgentRegistry`의 "역할이 다르다"는 기존 주석상 구분은, 실제로는 같은 실체(에이전트)를 바라보는 두 개의 창일 뿐이라 굳이 모델을 나눠 유지할 이유가 약합니다. 이중 트랙을 공식화(2번)하면 지금의 혼란을 오히려 정당화하는 꼴이 됩니다.
