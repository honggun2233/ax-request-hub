# AX Hub v23 구현 검토 — 기술 실행 vs 철학적 관점

**대상**: `v23-implementation-full-20260824.md` (Jarvis 구현, 데이터 프로비저닝·협의회·KPI/은퇴 플래그)
**검토일**: 2026-08-21
**주의**: 이 문서의 "v3 아키텍처"는 별도 기준 문서(2026-07-23)이며, 이 대화의 v3~v23 워크플로우 설계 시리즈와는 다른 문서입니다. 파일명의 "v23"은 우연히 겹친 번호일 뿐 직접 연결되지 않습니다.

---

## 검토 원칙

두 관점을 이렇게 연결해서 봅니다: **"규칙 하나가 기계적으로 실행되는 지점"마다, 거기에 AI가 판단 근거를 만들어 붙이는 순간 AX Hub의 철학이 심어집니다.** 이번 구현은 규칙 자동화(통제)는 잘 됐지만, 그 규칙이 왜 발동했는지·다음에 뭘 봐야 하는지를 사람에게 설명해주는 AI 레이어가 빠져 있습니다.

---

## 1. 기술적 관점 — 실행 시 문제될 수 있는 지점

### 잘된 점
- `admin/agents/flags/route.ts`에서 `AgentRegistry`에 없는 `department` 필드를 `owner`로 고친 것 — 스스로 잡아낸 버그
- `expire-check`·`inactive-check` 배치 둘 다 멱등성 확보 — 중복 실행돼도 안전
- 트랜잭션으로 상태전이+감사로그를 묶은 패턴이 파일 전체에 일관 적용

### 🔴 Critical — 배치 엔드포인트가 실제로 어떻게 호출되는지 불명확
```ts
export async function POST() {
  const auth = await requireRole("AX_TEAM");  // 세션 쿠키 기반 인증
```
`expire-check`·`inactive-check`는 "일 1회 실행 권장"인데 `requireRole()`은 사람의 세션 쿠키를 전제로 합니다. cron이 이 POST를 호출한다면 세션이 없어 매번 401이 납니다. 이전 middleware.ts 리뷰에서 지적한 "서비스 토큰 vs 세션 인증" 문제가 여기서도 재현됩니다.

**확인 필요**: 이 배치를 실제로 누가/어떻게 트리거할 계획인지(Vercel Cron, 외부 스케줄러, 수동 클릭 등). 스케줄러라면 `CRON_SECRET` 같은 별도 헤더 검증 경로가 `requireRole()`과 별개로 필요합니다.

### 🟠 High — 인증 체크 방식이 파일마다 다름
```
requireRole("AX_TEAM")                    ← 대부분의 라우트
getServerSession(authOptions) 직접 호출    ← dp/catalog GET
(session.user as any)?.email 직접 접근     ← data/requests/[id] PATCH
```
세 가지 패턴이 섞여 있습니다. 이게 예전 middleware.ts 부재의 원인이었던 "라우트마다 제각각 인증 체크"와 같은 유형의 문제입니다. 지금은 동작하더라도 새 라우트 추가 시 패턴 혼선으로 구멍이 생길 수 있습니다. `requireRole()`로 통일 권장.

### 🟠 High — `connectionRef` "시크릿 키만 저장"이 주석으로만 강제됨
```ts
if (!deliveryMode || !connectionRef?.trim() || !expiresAt) { ... }
// 값이 시크릿 매니저 키 참조인지 원문 자격증명인지 검증 없음
```
주석엔 "원문 저장 금지"라 돼 있지만 코드는 비어있지 않은지만 봅니다. 시크릿 매니저 키 형식(예: `vault://...` 프리픽스)을 정규식으로 강제하는 걸 권장.

### 🟡 Medium — 감사로그의 "누가 실행했는지" 기록이 배치 간 불일치
`inactive-check`는 `actorEmail: "SYSTEM"`이면서도 `detail.triggeredBy`에 실제 트리거한 사람을 남깁니다. `expire-check`는 `actorEmail: "SYSTEM"`만 있고 트리거한 사람이 안 남습니다.

### 🟡 Medium — 테스트 검증이 타입체크뿐
`npx tsc --noEmit` 통과는 타입만 보장하지 비즈니스 로직(GATE1→GATE2 선결조건, 3개월 연속 미달 판정 등)의 정확성은 검증하지 않습니다. 트랜잭션 배열 안 조건부 스프레드(`...(조건 ? [...] : [])`) 패턴은 조건 하나만 잘못돼도 조용히 빠지기 쉬운 구조라 별도 테스트 확인이 필요합니다.

## 2. 철학적 관점 — AX Hub다움이 빠진 지점

### 발견1 (★★★) — 데이터 카탈로그에 "영향도 질의" 자체가 없음

이미 확정됐던 방향: **"지식그래프는 영향도 질의 엔진으로, 데이터 자산 회수 시 승인화면에 '영향받는 에이전트 N개' 배지"**

```ts
// revoke/route.ts — 회수 시 연결된 PRODUCTION 에이전트 1건만 자동 SUSPENDED
const prodAgent = await prisma.agentRegistry.findFirst({
  where: { projectId: provision.request.projectId, phase: "PRODUCTION", prodStatus: "ACTIVE" },
```

기술적으로는 회수 시 연결 에이전트를 찾아 멈추는 로직이 있지만, 철학적으로는 이게 "질의 엔진"이 아니라 "1:1 하드코딩 조회"입니다. 다중 홉(이 데이터를 참조하는 다른 데이터 → 그걸 쓰는 다른 에이전트) 관계는 반영되지 않고, 회수 전에 "몇 개 에이전트가 영향받는지" 미리 보여주는 배지도 없습니다. **이미 결정됐던 우선순위 항목이 이번 구현 범위에서 빠졌습니다.**

### 발견2 (★★) — KPI 자동 플래그가 "왜"를 설명하지 않음

```ts
if (consecutiveMiss && !agent.retireFlag) {
  await prisma.agentRegistry.update({ data: { retireFlag: true } });
```

규칙(3개월 연속 60% 미달)은 정확히 자동화됐지만, 이전 설계의 P1(Gate3 채점근거 생성)과 같은 종류의 공백이 있습니다 — AX팀은 "왜 이 수치가 나왔는지, 폐기가 맞는지 아니면 전략적 가치로 유지해야 하는지"를 결국 원본 데이터를 다시 파봐야 압니다. 규칙은 자동화됐는데 판단을 돕는 설명은 없습니다.

### 발견3 (★★) — `dp/requests` 큐가 처음에 지적됐던 "옛날 스타일" 그대로 반복

```ts
// GET /api/dp/requests — status 필터만 있는 평범한 리스트
```

이게 대화 초반 "옛날 스타일로 드롭다운 선택하고 뭘 작성하고"라고 지적했던 패턴이 DATA_PLATFORM 심사자 쪽에서 반복된 것입니다. G3+본질업무 건이 뭐부터 급한지, 과거 유사 신청이 어떻게 처리됐는지를 AI가 먼저 정렬·요약해주는 레이어가 없어 심사자가 리스트를 처음부터 눈으로 훑어야 합니다.

## 3. 기술↔철학 연결 지점 정리

| 기술 작업 (지금 규칙만 있음) | 철학이 심어지는 지점 (AI 추가 필요) | 우선순위 |
|---|---|---|
| 데이터 카탈로그·프로비저닝 회수 | 다중홉 영향도 질의 엔진 + "영향받는 에이전트 N개" 배지 | ★★★ — 이미 확정됐던 항목이 빠짐 |
| KPI 자동 플래그(retireFlag) | 플래그 발동 시 "왜" 설명 + 유지/폐기 권고 근거 생성 | ★★ |
| DATA_PLATFORM 심사 큐 | 우선순위 자동정렬 + 유사사례 비교 브리핑 | ★★ |

**판단**: 셋 다 필요하지만 1번(영향도 질의 엔진)부터 처리해야 합니다 — 이미 결정됐던 우선순위를 이번 구현이 놓쳤다는 사실이 CTO 에이전트에게 명확히 전달돼야 하고, 나머지 둘은 그 위에 얹는 확장이라 순서가 뒤바뀌면 안 됩니다.
