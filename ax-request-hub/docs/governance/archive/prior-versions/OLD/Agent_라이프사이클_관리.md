## 1. 관리 범위 — 무엇을 "관리 대상 Agent"로 보는가

모든 AI 활용이 라이프사이클 관리 대상은 아니다.

| 유형 | 관리 대상? | 이유 |
|------|-----------|------|
| 임직원 개인 AI 도구 사용 (G1) | ❌ 불필요 | 자동화 없음, 개인 생산성 |
| APA (고정 워크플로우 자동화) | ✅ 파이프라인 등록 | 자동 실행, 사람 개입 줄어듦 |
| 단독 에이전트 (파일럿 통과) | ✅ Agent 등록 | 자율 판단, 라이프사이클 추적 필요 |
| 멀티 에이전트 시스템 | ✅ 시스템 등록 + 개별 에이전트 등록 | 복잡한 의존성 관리 필요 |

**기준**: 자동화 실행되고 + 사람 승인 없이 반복 동작하면 등록 대상

## 2. Agent 등록 기준

### 2-1. 등록 시점
- 파일럿 → 운영 승격 게이트 통과 즉시 등록
- (파일럿 중에는 실험 상태, 등록 아님)

### 2-2. 등록 신청 필수 항목

```
[Agent 등록 신청서]

1. Agent 이름 (기능을 명확히 표현):
   예) 공시_자동분류_에이전트, ETF_리서치_어시스턴트

2. 유형 (APA / 단독 / 멀티):

3. 담당 부서 / 운영 담당자 (사람):

4. 목적 (한 문장):

5. 데이터 접근 범위:
   - 읽는 데이터:
   - 쓰는 데이터:
   - 기밀등급: G1 / G2 / G3

6. 사용 AI 모델:

7. 외부 API 연동 목록:

8. Human-in-the-loop 포인트 (어디서 사람이 검토하는가):

9. 실행 주기 (실시간 / 일배치 / 요청 기반):

10. 실패 시 행동 (알림 / 자동 롤백 / 일시정지):

11. 연관 과제 ID (AX Request Hub):
```

## 3. Agent ID 체계

### 3-1. ID 형식

```
AX-{YYYY}-{유형코드}-{순번3자리}

예:
AX-2026-APA-001   → 2026년 첫 번째 APA
AX-2026-AGT-001   → 2026년 첫 번째 단독 에이전트
AX-2026-MAS-001   → 2026년 첫 번째 멀티 에이전트 시스템
```

### 3-2. 유형 코드

| 코드 | 유형 |
|------|------|
| APA | AI-Powered Automation |
| AGT | 단독 에이전트 (Single Agent) |
| MAS | 멀티 에이전트 시스템 (Multi-Agent System) |

### 3-3. ID 발급 절차
1. 등록 신청서 제출 → AX팀 검토
2. AX팀이 순번 발급 → AX Request Hub에 등록
3. 개발팀에 ID 통보 (코드·설정 파일에 반영)

## 4. Agent 라이프사이클 상태

```
[등록 신청] → [활성(Active)] → [일시정지(Suspended)] → [폐기(Retired)]
                                       ↑ ↓                      ↓
                                   [문제 해결]               [아카이브]
```

| 상태 | 정의 | 전환 조건 |
|------|------|----------|
| 🟢 **Active** | 정상 운영 중 | 운영 승격 후 |
| 🟡 **Suspended** | 일시 정지 | 보안 이슈 발견 / KPI 급락 / 현업 요청 |
| 🔴 **Retired** | 폐기 | 폐기 기준 충족 (아래 참조) |
| 📦 **Archived** | 기록 보존 | Retired 후 90일 경과 |

### 4-1. 폐기 기준 (다음 중 하나라도 해당되면)

| 기준 | 판단 방법 |
|------|---------|
| KPI 목표 60% 미달 3개월 연속 | AX 대시보드 자동 감지 → 팀장 보고 |
| 보안 사고 1건 이상 발생 | 즉시 Suspended → 검토 후 Retired |
| 관련 업무 프로세스 자체 소멸 | 담당 부서장 폐기 신청 |
| 더 나은 솔루션으로 대체 확정 | 신규 에이전트 Active 전환 시 |
| 1년 이상 사용량 0 | CDO 자동 탐지 → AX팀 확인 |

### 4-2. 폐기 절차
1. 폐기 사유 기록 (누가, 언제, 왜)
2. 현업 담당자 사전 통보 (최소 2주 전)
3. 대체 솔루션 안내 또는 수동 전환 지원
4. 데이터·로그 아카이브 (90일 보존)
5. API 키·접근권한 회수
6. AX Request Hub에 Retired 상태 기록

## 5. 파이프라인 관리 — 어디까지 추적할 것인가

에이전트가 의존하는 파이프라인을 추적해야 장애 영향 범위를 안다.

### 5-1. 등록 필수 파이프라인 항목

| 항목 | 내용 |
|------|------|
| 데이터 소스 | 어떤 DB/API/파일에서 데이터를 가져오는가 |
| 데이터 싱크 | 결과를 어디에 저장/전송하는가 |
| 트리거 | 무엇이 에이전트를 실행시키는가 (스케줄/이벤트/수동) |
| 외부 의존성 | 다른 에이전트, 외부 API, 사내 시스템 |
| 장애 시 영향 | 이 에이전트가 멈추면 어떤 업무가 영향받는가 |

### 5-2. 의존성 그래프 관리 원칙
- 에이전트 A가 에이전트 B의 결과에 의존하면 → B 폐기 전 A 먼저 처리
- 순환 의존성(A→B→A) 금지
- 단일 에이전트에 5개 이상 다른 에이전트가 의존하면 → 아키텍처 재검토

### 5-3. 정기 파이프라인 점검

| 주기 | 점검 항목 |
|------|---------|
| 주간 | 실패 실행 건수, 지연 여부 |
| 월간 | 비용 대비 처리량, 의존 시스템 변경 이력 |
| 분기 | 전체 파이프라인 의존성 다이어그램 업데이트 |
