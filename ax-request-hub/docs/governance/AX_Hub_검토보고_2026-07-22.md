## 요약

문서 계층 구조(규정→정책→지침/표준/매뉴얼)와 공식 문서-보완 문서 참조 추적 방식은 잘 설계되어 있다. 다만 교차 검증 결과 **규정 리스크 3건(P1), 아키텍처 정합성 이슈 3건(P2), 문서·역할·운영 보완 사항(P3)** 이 확인되었다. P1은 금융회사 컴플라이언스와 직결되므로 우선 조치가 필요하다.

## P1 — 규정 리스크 (즉시 조치)

### 1-1. G3(기밀) 데이터의 외부 API 전송

- **현상**: 신청서 전문이 Claude API(외부 SaaS)로 전송되어 6차원 자동평가를 수행. 신청서 내용 자체가 G3일 수 있으나, 현재 플로우는 평가 이후에 G3를 에스컬레이션하는 순서.
- **리스크**: AX-REGULATION-2026-001 제1조 기밀등급 취지와 충돌 소지. 기밀 정보의 외부 전송 선례가 됨.
- **조치안** (택1 후 규정·시스템 동시 반영):
  - A. 기밀등급 판단을 평가보다 **선행** → G3 판정 시 자동평가 생략, 즉시 AX팀 수동 검토
  - B. 기밀 필드 마스킹/요약 후 평가 (마스킹 기준을 개발표준에 명세)
- **반영 위치**: AX-REGULATION 제4조, `AX_AI개발플로우_추가조항.md`, `/api/projects` 처리 로직

### 1-2. Telegram 알림 채널

- **현상**: Gate 2 보류 시 Telegram으로 알림 발송.
- **리스크**: 금융회사 업무 통지를 외부 개인 메신저로 발송 → 망분리·기록보존 관점 컴플라이언스 지적 가능.
- **조치안**: 사내 메일/사내 메신저로 대체. 불가피하게 유지 시 알림 채널 정책(발송 내용 범위, 기록 보존 방식)을 문서화.
- **반영 위치**: AX-MANUAL-2026-001, architecture.md §2·§5

### 1-3. 이의제기(재심) 절차 부재

- **현상**: 자동승인/반려 결정에 대해 신청자가 재심을 요청하는 경로가 규정·API 어디에도 없음. `/api/evaluate`는 ADMIN 전용 재평가뿐.
- **리스크**: AI가 승인 여부를 결정하는 시스템에서 이의신청 절차 부재는 거버넌스 결함.
- **조치안**: AX-REGULATION 제4~5조 부근에 이의신청 조항 신설 + `/api/projects/[id]/appeal` 류 API 추가 (신청자 권한, AX팀 재심 SLA 명시).

## P2 — 아키텍처 내부 정합성 (설계 정리)

### 2-1. Agent vs AgentRegistry 이중 모델

- **현상**: 에이전트 라이프사이클 상태가 `AgentRegistry`(레지스트리·Gate·KPI)와 `Agent`(폐기 관리·KPI·상태) 두 모델에 분산.
- **문제**: 설계 원칙으로 선언한 "Prisma + SQLite = SSOT"와 자기모순. 상태 불일치 발생 가능.
- **조치안**: 단일 모델로 통합 권장. 유지가 불가피하면 두 모델의 역할 경계·동기화 규칙·마스터 지정을 architecture.md에 명시.

### 2-2. 상태 체계 3종 병존, 매핑 미정의

- **현상**:
  - §2 플로우: submitted → pilot → ACTIVE → RETIRE_CANDIDATE
  - §7 상태도: ACTIVE / SUSPENDED / DEPRECATED / RETIRED
  - §8 Gate 단계: GATE1 → GATE2 → GATE3
- **문제**: 세 체계 간 매핑 정의 없음. 특히 **pilot → ACTIVE 전환 조건**(기간, KPI 기준, 승인 주체)이 어디에도 없음.
- **조치안**: 통합 상태 전이표 1장 작성 (`registry-lifecycle-design.md`에 편입), pilot 졸업 기준 명문화.

### 2-3. API 권한 표기 오류 추정

- **현상**: `/api/governance-docs` POST 권한이 ALL. 문서 등록이 전직원 가능하면 `/admin/docs`와 충돌.
- **조치안**: ADMIN 오기인지 실제 권한 버그인지 코드 확인 후 수정. 겸사겸사 API 권한 테이블 전수 점검 권장.

## P3 — 문서·역할·운영 보완

### 3-1. 문서체계 인덱스의 시스템 연결 구조도 갱신

- 현행 mermaid 구조도는 architecture.md 대비 축약: `/chat`, `/status`, `/me/tools`, `/me/usage`, `/admin/retired`, `/admin/skills`, `/admin/docs` 누락.
- E2(/skills)·E3(/docs)·E4(/me/*)가 관리 노드와 연결되지 않은 고립 노드 → E2↔/admin/skills, E3↔/admin/docs 등 데이터 흐름 연결 필요.

### 3-2. 거버넌스 문서 공백 3건 (시스템은 있으나 문서 없음)

| 영역 | 시스템 구현 | 필요 문서 |
|------|-------------|-----------|
| AI 스킬 라이브러리 | /skills, Skill, SkillRating | 스킬 등록 기준, 검수 절차(부적절 프롬프트 필터링), 평가 운영 기준 |
| AI 리터러시 레벨 L0~L4 | LevelApplication, LevelHistory | 레벨 정의, 심사 기준, 권한 연계 |
| 토큰 정책 | TokenPolicy, DistributionPolicy, UsageAlert 등 5개 모델 | 배분·회수·알림 임계값 운영 기준 (AX-MANUAL-2026-002는 계정만 커버) |

### 3-3. 역할 체계

- **EXECUTIVE 역할 신설**: `/executive`가 C레벨 대시보드인데 권한이 ADMIN → 경영진용 읽기 전용 역할 분리.
- **부서장 사전 확인 단계**: 현재 직원이 /submit → 바로 자동평가. 부서장이 모르는 과제가 자동승인될 수 있음 → 신청 플로우에 부서장 확인(또는 사후 통보) 단계 조직적 수용 여부 검토.
- **DEPT_HEAD 지정 절차**: 누가 부서장 권한을 부여하는지 문서·시스템 모두 미정의.

### 3-4. 미결사항(§18) 추가 항목

- SQLite → PostgreSQL 전환 (전사 시스템 동시성·백업·다중 인스턴스 한계)
- 감사로그 보존기간·위변조 방지 명세 (전자금융감독규정 관점)
- 시크릿 관리 체계 (NEXTAUTH_SECRET, ANTHROPIC_API_KEY 사내 배포 시)
- 이의제기 API (P1-3 연계)
- KPI "3개월 60% 미달" 자동 판정 로직의 실행 주체(배치? 수동?) 명확화

### 3-5. 문서체계 자체 개선

- `AX_전사AI운영체계_제안_2026-07.md`는 제안서인데 상태(초안/검토중/승인) 구분이 없음 → 문서 목록 테이블에 **상태 컬럼** 추가.
- `registry-lifecycle-design.md`가 "공식 문서 → 보완 문서 참조 현황" 테이블에 없음 → 어느 조항(AX-POLICY 제 몇 조)을 보완하는지 명시.
