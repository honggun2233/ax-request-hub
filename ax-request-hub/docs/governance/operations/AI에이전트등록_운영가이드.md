# AI 에이전트 등록·통제 지침

> 문서번호: IT-AX-OPS-003 | 버전: v1.2 | 2026-07-14
> 소관: AX/PI센터 AX팀
> 적용: AX팀·임직원·현업 부서장

---

## 제1장 총칙

### 제1조(목적)

이 지침은 「AI 운영 규정」(AX-REGULATION-2026-001)에서 위임한 사항과 AI 에이전트의 위험등급별 통제, 라이프사이클 관리, 자원·비용 통제에 필요한 세부 기준을 정함을 목적으로 한다.

### 제2조(적용 범위)

① 이 지침은 AX팀, 임직원 및 현업 부서장에게 적용한다.

② 유형 3·4 에이전트 및 G2·G3 데이터를 처리하는 과제는 이 지침의 통제 요건을 의무적으로 준수하여야 한다.

### 제3조(용어의 정의)

이 지침에서 사용하는 용어의 정의는 다음과 같다.

① "위험등급"이란 AI 과제가 업무·데이터·유형 기준에서 갖는 잠재적 위해 수준을 고위험·중위험·저위험으로 구분한 것을 말한다.

② "Agent ID"란 AX팀이 에이전트에 발급하는 고유 식별자를 말한다.

③ "라이프사이클"이란 에이전트가 생성되어 폐기될 때까지의 전체 상태 흐름을 말한다.

④ "Kill Switch"란 에이전트를 즉시 중단시키는 Circuit Breaker 패턴의 제어 장치를 말한다.

## 제2장 위험등급별 통제 요건

### 제4조(위험등급 결정)

① 위험등급은 다음 순서로 결정한다.

1. 업무 분류 → 규정 제8조 목록 대조
2. 기밀등급 → G3 포함 시 고위험 자동 상향 / G2만이면 최소 중위험
3. 유형 → 유형 3·4이면 최소 중위험
4. 영향 범위 → 고객 자산·계약 영향이면 고위험 자동 상향

② 등급이 명확하지 않은 경우 상위 등급으로 분류한다.

### 제5조(고위험 필수 통제)

고위험 과제에 대하여 다음 각 호의 통제를 의무적으로 적용한다.

| 항목 | 기준 |
|------|------|
| Human-in-the-loop | 담당자 + 팀장 이중 검토 후 실행 |
| 독립 검증 | 개발팀과 독립된 부서가 별도 검증 |
| 출처 강제 | 모든 AI 응답에 근거 데이터·출처 명시 |
| 감사 로그 | 입력→처리→출력 전 과정 기록, 5년 보존 |
| 사전 승인 | 유형 3·4 적용 시 AX팀장 + 팀 상위 승인 |
| Kill Switch | Circuit Breaker 구현 의무 |
| 롤백 절차 | 운영 중 장애 발생 시 이전 버전·수동 처리로 즉시 전환하는 절차를 사전 정의 |

### 제6조(감사 로그 필수 필드)

고위험 과제의 감사 로그에는 다음 항목을 반드시 기록하여야 한다.

| 필드 | 내용 |
|------|------|
| timestamp | UTC 기준 ISO 8601 |
| agent_id | AX팀 발급 Agent ID |
| event_type | llm_call / tool_call / human_checkpoint / error |
| input_summary | 입력 요약 (G3 원문 제외) |
| output_summary | 출력 요약 |
| tool_name | 호출한 도구명 (tool_call 시) |
| user_id | 요청자 또는 트리거 시스템 식별자 |
| decision | 사람 검토 결과 (human_checkpoint 시) |

### 제7조(고위험 운영 승격 기준)

고위험 과제의 운영 승격은 다음 기준에 따른다.

| 단계 | 기간 | 기준 | 승인 |
|------|------|------|------|
| PoC | 2주 | 기술 실현 가능성 확인 | AX팀장 |
| 파일럿 | 8주 | KPI 80% 이상 + 사고 0건 | 팀 상위 |
| 운영 승격 (일반) | — | KPI 90% 이상 + 감사 로그 완비 | 팀 상위 + 준법감시인 |
| 운영 승격 (투자·운용 실행·공시·컴플라이언스 판정 해당) | — | KPI 90% 이상 + 감사 로그 완비 | 팀 상위 + 준법감시인 + AX 위원회 최종 승인 |

### 제8조(중위험 필수 통제)

중위험 과제에 대하여 다음 각 호의 통제를 의무적으로 적용한다.

| 항목 | 기준 |
|------|------|
| 사람 검토 후 확정 | AI 산출물은 초안. 담당자 검토 후 최종 확정 |
| 출처 명시 | 사실 주장 시 근거 출처 포함 |
| 분기별 KPI 점검 | 정확도·사용률·오류율 점검 |
| 과제 등록 의무 | 유형 2 이상 → AX팀 과제 등록 후 운영 |

### 제9조(중위험 운영 승격 기준)

중위험 과제의 운영 승격은 다음 기준에 따른다.

| 단계 | 기간 | 기준 | 승인 |
|------|------|------|------|
| PoC | 2주 | 기술 실현 가능성 확인 | AX팀장 |
| 파일럿 | 4~6주 | KPI 60% 이상 | AX팀장 + 현업 부서장 |
| 운영 승격 | — | KPI 80% 이상 + 사고 0건 | 팀 상위 |

### 제10조(위험등급 재평가)

① 다음 각 호의 상황이 발생하면 즉시 위험등급을 재평가하여야 한다.

1. 적용 업무 범위가 최초 등록보다 확대된 경우
2. 더 높은 기밀등급의 데이터를 새로 처리하게 된 경우
3. 관련 법령·감독지침이 개정된 경우

② 연간 정기 재평가는 매년 1월에 실시한다.

## 제3장 에이전트 라이프사이클

### 제11조(라이프사이클 구분)

에이전트 라이프사이클은 생성 라이프사이클(Phase Gate 1→7)과 관리 라이프사이클(상태 머신)로 구분한다. 두 라이프사이클은 Phase 6 파일럿 진입 시점에 교차한다.

### 제12조(사전 설계 체크)

유형 3·4 에이전트는 운영 전 AX팀과 다음 항목을 반드시 확인하여야 한다.

| 항목 | 확인 사항 |
|------|---------|
| 목표 | 에이전트가 달성하는 구체적인 결과물은 무엇인가. 목표가 두 개 이상이면 에이전트를 분리한다. |
| 범위 | 절대 하면 안 되는 것 목록을 시스템 프롬프트에 명시했는가 |
| 도구 | 목표에 필요한 최소한의 도구만 허용했는가 |
| Human Checkpoint | 고위험 결과 전 사람 승인 포인트가 있는가 |
| Kill Switch | 즉시 중단 조건과 중단 후 행동이 정의되어 있는가 |
| 감사 추적 | 모든 Tool Call과 판단 근거를 기록하는가 |
| 실패 모드 | 실패 시 행동(알림·롤백·중단)이 정의되어 있는가 |
| 평가 KPI 사전 합의 | 과제 정의서 v1에 측정 가능한 KPI 목표값이 기재되었는가 |

### 제13조(Agent ID 체계)

① Agent ID 형식은 다음과 같다.

```
형식: AX-{YYYY}-{유형코드}-{순번}
유형코드: AGT (단독 에이전트) / MAS (멀티 에이전트 시스템)
예: AX-2026-AGT-001
멀티 에이전트 서브: AX-2026-MAS-001-SUB-A

임시 ID (파일럿 전용): AX-DEV-{YYYY}-{순번}
예: AX-DEV-2026-001 → 운영 전환 시 정식 ID로 교체
```

② Phase 및 데이터등급에 따른 Agent ID 발급 기준은 다음과 같다.

| 상황 | ID 유형 | 발급 주체 | 데이터 접근 |
|------|--------|---------|-----------|
| G1 개인 실험 (Phase 2~3) | 없음 | — | G1만 (샌드박스 권장) |
| G1 팀 공유 PoC (Phase 4~5) | 없음 | AX팀 인식·등록만 | G1, 샘플 데이터 |
| Phase 6 파일럿 (G1/G2) | AX-DEV- (임시) | AX팀 | G1/G2, 제한 실데이터 |
| Phase 7 운영 | AX-YYYY-AGT-XXX (정식) | AX팀 | 설계 기준 전체 접근 |

### 제14조(생성 라이프사이클)

Phase별 ID 상태, 에이전트 상태, 데이터 접근 범위는 다음과 같다.

| Phase | 명칭 | ID 상태 | 에이전트 상태 | 데이터 접근 | AX팀 역할 |
|-------|------|--------|-------------|-----------|---------|
| 0 | 발굴 | 없음 | — | G1만 | 존재 인식 |
| 1 | 기획 | 없음 | — | G1만 | 과제 등록 |
| 2 | 설계 | 없음 | — | G1, 샘플 | 기술 검토·설계 지원 |
| 3 | MVP | 없음 | 개발 중 | G1, 샘플 | AX팀 인식·등록 |
| 4 | 심사 | 없음 | 심사 중 | G1, 샘플 | 심사 보고서 작성 |
| 5 | 파일럿 | AX-DEV- (임시) | 🟡 등록신청 | G1/G2, 제한 실데이터 | 임시 ID·파일럿 운영 |
| 6 | 운영 | AX-YYYY-AGT-XXX (정식) | 🟢 Active | 설계 기준 전체 | 정식 ID·모니터링 활성화 |

### 제15조(관리 라이프사이클)

① 운영 중 에이전트의 상태 전환 기준 및 조치는 다음과 같다.

| 상태 전환 | 조건 | AX팀 역할 |
|---------|------|---------|
| → 🟡 등록신청 | Phase 6 파일럿 진입 승인 | 임시 ID 발급, 인벤토리 신규 등록 |
| 🟡 → 🟢 Active | Phase 7 운영 승격 | 정식 ID 교체, KPI 모니터링 활성화 |
| 🟢 → 🔵 Suspended | 사고·점검·업무 변화 | 원인 분석, 접근권한 일시 차단 |
| 🔵 → 🟢 Active | 원인 해소 후 복구 승인 | 복구 검토, 재활성화 |
| * → 🔴 Retired | 폐기 기준 충족 | ID 비활성화, 인벤토리 폐기 등록, 접근권한 전체 회수 |

② 다음 각 호의 기준 중 하나에 해당하면 에이전트를 폐기한다.

1. KPI 달성률 60% 미달 3개월 연속 (제15조의2에서 정의한 측정 방식 적용)
2. 데이터 유출·보안 사고 발생
3. 12개월 연속 미사용 (lastUsedAt 기준, Hub 자동 감지)
4. 담당 업무 소멸

③ 폐기 후 감사 로그는 보존 기간을 유지한다. Agent ID는 재사용을 금지한다.

### 제15조의2(KPI 정의 및 성과 측정 기준)

① 에이전트 등록 시 다음 세 항목을 반드시 입력하여야 한다. 입력 없이는 운영 승격(Phase 7)을 허용하지 않는다.

| 필드 | 설명 | 예시 |
|------|------|------|
| KPI 지표명 | 측정하는 결과물 | 공시 분류 정확도 |
| 목표값 | 달성 기준 (수치) | 90% 이상 |
| 측정 방법 | 어떻게 측정하는가 | 월 100건 샘플 사람 검수 비교 |
| 측정 주기 | 언제 측정하는가 | 월 1회, AX팀 입력 |

② KPI 유형은 업무 특성에 따라 다음 중 하나로 설정한다.

| 유형 | 대상 에이전트 | 지표 예시 |
|------|------------|---------|
| 정확도형 | 분류·추출·변환 | 정확도(%), 오류율(%) |
| 완료율형 | 태스크 실행·자동화 | 태스크 성공 완료율(%) |
| 시간절감형 | 반복업무 대체 | 처리 시간 단축(시간/월) |
| 만족도형 | 작성·요약·응답 | 재작업 요청 빈도(건/월), 사용자 만족도(5점) |

③ 토큰 사용량은 성과 지표로 사용하지 않는다. 토큰 비용은 별도 비용 통제 지표로만 관리한다.

④ 성과 평가는 **성과/비용 2차원 매트릭스**로 분기 1회 실시한다.

```
              성과 달성률
             높음(≥60%)  │  낮음(<60%)
토큰비용  낮음 │  ★ 확산 후보  │  △ 개선 지시
             ────────────┼────────────
         높음 │  ○ 최적화 권고  │  ✗ 폐기 우선 대상
```

- ★ 확산 후보: AX협의체에 전사 확산 안건으로 상정
- ✗ 폐기 우선 대상: 즉시 Suspended 전환 후 30일 내 개선 없으면 폐기

⑤ KPI 달성률 산출 방식: `(실제 측정값 / 목표값) × 100`. 단, 시간절감형은 `(목표 절감 시간 대비 실제 절감 시간) × 100`으로 산출한다.

### 제15조의3(자동 추적 및 알림)

① Hub 시스템은 운영 중 에이전트에 대해 다음 항목을 자동으로 추적한다.

| 추적 항목 | 방법 | 알림 조건 |
|---------|------|---------|
| 마지막 사용일 (lastUsedAt) | 에이전트 호출 시 자동 갱신 | 6개월 미사용 시 경고, 12개월 시 폐기 후보 플래그 |
| KPI 입력 누락 | 월 1회 배치 확인 | 미입력 에이전트 AX팀에 알림 |
| KPI 미달 연속 횟수 | AX팀 월 입력 후 자동 집계 | 2개월 연속 미달 시 경고, 3개월 시 폐기 후보 플래그 |

② 폐기 후보 플래그가 부여된 에이전트는 다음 달 AX협의체 안건으로 자동 상정된다.

③ 에이전트 담당자(등록자)에게는 플래그 부여 즉시 이메일 알림을 발송한다.

### 제15조의4(ETF 앙상블 에이전트 Gate 라이프사이클)

① IT업무개발팀이 운영하는 ETF 앙상블 에이전트군(Quantitative Agent, 이하 "ETF 에이전트")은 범용 Phase 기반 라이프사이클(제14조·제15조)과 별도로 Gate 기반 전문 라이프사이클을 적용한다.

② Gate 기반 라이프사이클 단계 및 통과 기준은 다음과 같다.

| 단계 | 의미 | 통과 기준 | 담당 |
|------|------|-----------|------|
| DEVELOPING | 코드 작성 중, QA 미제출 | 기능 구현 PR 머지 | CTO (IT개발) |
| GATE1 | 기능 검증 | fallback율 ≤ 30%, AgentSignal 정상 반환 | QA (독립 검수) |
| GATE2 | 도메인 검증 | SAM LAB 30일 누적 정확도 ≥ 55%, 운용역 신뢰점수 ≥ 3/5 | 운용역 (ETF운용팀) |
| GATE3 | 스트레스 검증 | 이상값·데이터없음 상황에서 크래시 0건, fallback 정상 처리 | QA (독립 검수) |
| ACTIVE | 앙상블 운영 중 | 3 Gate 모두 통과 | — |
| DEGRADED | 성능 저하 감지 | 정확도 < 50% 또는 fallback율 > 70%, 2주 연속 | 자동 감지 |
| RETIRED | 폐기 완료 | 운용역·IT개발팀 합의 후 수동 처리 | 운용역 |

③ Gate2 도메인 검증의 정확도 측정은 SAM LAB(가상펀드 플랫폼, http://<사내AX서버>/samlab)에서 30일 누적 운용 데이터를 기준으로 한다. SAM LAB 가동 시작일(2026-07-14) 기준 Gate2 측정 가능 최초일은 2026-08-13이다.

④ 운용역 Gate2 리뷰 절차는 다음과 같다.

1. SAM LAB 대시보드에서 해당 에이전트의 30일 Score 추이·정확도 확인
2. AX Hub 에이전트 레지스트리(http://<사내AX서버>/registry)에서 해당 에이전트 슬라이드오버 열기
3. 신뢰점수(1~5점) 선택 및 도메인 관점 코멘트 입력
4. "Gate3 스트레스로 진행" 버튼으로 단계 전환

⑤ ETF 에이전트 라이프사이클의 관리 시스템은 AX Hub 에이전트 레지스트리(IT-AX-OPS-003 소관 시스템)로 한다. 단계 전환 이력은 동 시스템에 자동 기록된다.

⑥ ETF 에이전트의 DEGRADED 자동 감지 기준은 다음과 같으며, 해당 조건 충족 시 AX Hub가 단계를 자동 전환하고 운용역에게 알림을 발송한다.

| 조건 | 기간 |
|------|------|
| SAM LAB 30일 정확도 < 50% | 2주 연속 |
| fallback율 > 70% | 2주 연속 |

⑦ ETF 에이전트의 폐기(RETIRED) 처리는 운용역과 IT업무개발팀장의 합의를 거쳐야 하며, 폐기 사유를 AX Hub 레지스트리에 기록한다. Agent ID는 재사용을 금지한다.

## 제4장 자원·비용 관리

### 제18조(예산 편성)

AI 과제 관련 예산 편성·승인·집행 기준은 별도 사규에 따른다. AX팀은 과제별 예상 비용을 과제 정의서 v1에 명시하고 해당 사규 절차에 따라 예산을 신청한다.

### 제19조(API 키 관리)

① API 키 발급 및 관리 기준은 다음과 같다.

| 용도 | 발급 방법 | 조건 |
|------|---------|------|
| G1 개인 실험 (Phase 2~3) | CREW가 직접 발급 가능 | 발급 후 AX팀 키 목록에 등록만 |
| G1 팀 공유·파일럿 이상 | AX팀 신청 → 과제별 키 발급 | 과제 등록 선행 필수 |
| G2 이상 모든 용도 | AX팀 신청 필수 | G2 접근 사전 사전 승인 후 발급 |

② 다음 각 호의 공통 원칙을 준수하여야 한다.

1. 코드 하드코딩 금지 → `.env` 파일 저장, `.gitignore` 필수
2. `.env` GitHub 업로드 금지 → 발견 즉시 키 무효화
3. 공유 폴더·이메일·메신저로 키 전달 금지

### 제20조(토큰 사용량 관리)

① AX팀은 과제별 토큰 사용량을 추적·통제할 책임을 진다. 토큰 비용은 AI 운영 원가이며, 과제별 사용량을 추적하지 않으면 예산 초과와 낭비가 발생해도 인지할 수 없다.

② 계층형 예산 구조는 다음과 같다. 상위 예산을 초과하면 하위 예산 집행이 자동 차단된다.

| 계층 | 단위 | 설정 주체 | 초과 시 |
|------|------|---------|--------|
| 전사 월 예산 | 전체 AI API 비용 상한 | 팀 상위 | 신규 과제 착수 금지 |
| 과제별 월 예산 | 과제 정의서 v1 기재 금액 | AX팀장 | 해당 과제 자동 정지 |
| 호출별 상한 | 단일 LLM 호출 최대 토큰 | AX 엔지니어 | 호출 거부 후 에러 반환 |

③ Attribution Tagging — 모든 LLM 호출에 다음 태그를 부착하여 사용처를 추적한다.

```
agent_id: AX-2026-AGT-001     # Agent ID
task_type: summarize           # 호출 목적 (분류·생성·검토 등)
data_class: G1                 # 데이터 기밀등급
```

과제마다 API 키를 분리 발급하고, 태그 누락 호출은 집계 시스템에서 별도 플래그 처리한다.

④ 실시간 집행 기준은 다음과 같다.

1. 월 예산 80% 도달 시 자동 알림 — AX팀장·담당 CREW에게 통보
2. 월 예산 100% 도달 시 처리 방식은 위험등급별로 사전 결정한다. G1·저위험은 알림 후 담당자 판단, G2 이상·고위험은 자동 정지를 원칙으로 한다.
3. 전주 대비 사용량 200% 초과 시 이상 급증 알림 — AX팀이 원인 파악 후 24시간 내 조치한다.

⑤ 컨텍스트 최적화 원칙은 다음과 같다.

1. **Prompt Caching 우선**: 동일 입력이 반복되는 구간(시스템 프롬프트·참조 문서)에는 캐싱을 의무 적용한다. 미적용 시 이관 완성도 심사에서 감점한다.
2. **모델 등급 라우팅**: 분류·라우팅·키워드 추출처럼 정형화된 작업은 경량 모델을 사용하고, 복잡한 추론이 필요한 경우에만 상위 모델로 올린다. 상위 모델을 기본으로 사용하는 것을 금지한다.
3. **컨텍스트 정리**: 에이전트 시스템 프롬프트에 불필요한 예시·주석을 제거하고, 각 호출에 필요한 최소 컨텍스트만 포함한다.
4. **사용량 명시**: 과제 기획 시 월 예상 토큰 사용량(입력·출력 토큰 구분)을 과제 정의서 v1에 기재한다. 실측치와 예상치의 차이가 50% 이상이면 AX팀이 원인을 파악하고 다음 분기 예산에 반영한다.

### 제21조(모델 배분 정책)

① 삼성자산운용 AI 인프라는 OpenAI(GPT), Anthropic(Claude), Google(Gemini) 세 공급사를 지원한다. 사용자가 원하는 모델을 임의로 선택하는 것을 금지하며, CREW 등급·과제 위험등급·데이터 기밀등급을 기준으로 AX팀이 배분한다.

② CREW 등급별 허용 모델은 다음과 같다.

| CREW 등급 | 허용 모델 | 접근 경로 | 비고 |
|---------|---------|---------|------|
| Lv.1 탐색 | GPT Enterprise (Copilot), Claude.ai (Enterprise) | 사내 SSO 통합 도구 | 개인 API 키 발급 불가 |
| Lv.2 실험 | 위 Lv.1 + AX 샌드박스 API (Sonnet·GPT-4o·Gemini 1.5 Flash) | AX팀 발급 공유 키 | 샌드박스 전용, G1 데이터만 |
| Lv.3 개발 / AX 엔지니어 | 모든 모델 (과제 위험등급 기준 준수) | 과제별 전용 API 키 | 기밀등급 경로 준수 의무 |

③ 과제 위험등급·데이터 기밀등급에 따른 모델 배분 기준은 다음과 같다.

| 위험등급 / 기밀등급 | 허용 모델 계열 | 배포 경로 |
|----------------|------------|---------|
| 저위험 / G1 | GPT Enterprise, Claude Sonnet, Gemini 1.5 Pro | MS Copilot, Claude.ai, Google Workspace |
| 중위험 / G1~G2 | Claude Sonnet (Bedrock), GPT-4o (Azure) | AWS Bedrock VPC, Azure Private Endpoint |
| 고위험 / G2~G3 | 온프레미스 LLM 또는 Bedrock 격리 VPC | 사내 서버 전용 (외부 전송 금지) |
| 고위험 / G3 (투자·운용 실행) | 온프레미스 LLM 전용 | 온프레미스 (인터넷 차단 환경) |

④ 모델 선택 세부 기준은 다음과 같다.

| 용도 | 권장 모델 | 이유 |
|------|---------|------|
| 일반 요약·초안 생성 | Claude Sonnet, GPT-4o | 비용·품질 균형 |
| 대량 분류·라우팅·키워드 추출 | Claude Haiku, Gemini 1.5 Flash | 저비용 고속 처리 |
| 복잡 추론·법률·컴플라이언스 검토 | Claude Opus (과제 정의서 명시 시만) | 최상위 추론 성능 |
| 코드 생성·리뷰 | GPT-4o, Claude Sonnet | 코드 도메인 강점 |
| 멀티모달(이미지·문서 OCR) | GPT-4o Vision, Gemini 1.5 Pro | 시각 처리 강점 |

⑤ 다음 행위는 금지한다.

1. 최상위 모델(Opus 계열)을 비용 검토 없이 기본 모델로 설정하는 것
2. 과제 정의서에 명시되지 않은 모델을 운영 중 임의로 교체하는 것
3. G2 이상 데이터를 외부 클라우드 API(Bedrock·Azure 격리 VPC 외)로 전송하는 것
4. 공급사 선택을 사용자 선호만으로 결정하는 것

⑥ 모델을 교체할 때는 과제 정의서 모델 항목을 수정하고 AX팀 검토를 거쳐야 한다. 교체 전·후 성능 비교 테스트 결과를 커밋 메시지에 기록한다.

### 제22조(조직 지식 축적 성숙도 평가)

① AI Native 조직의 핵심 지표는 "얼마나 썼는가"가 아니라 "쓴 만큼 조직 지식이 남았는가"이다. AI를 많이 써도 그 과정이 기록·재사용·이전되지 않으면 비용만 늘고 역량은 그대로다. 이 조항은 그 축적 수준을 세 단계로 측정한다.

② 1단계 — **기록**: 만든 것을 남겼는가 [분기 측정, 정량]

AI 활용 결과가 다음 번에도 쓸 수 있는 형태로 저장되고 있는지를 측정한다.

| 지표 | 무엇을 측정하는가 | 목표 | 측정 시점 |
|------|---------------|------|---------|
| 과제 정의서 완료율 | 등록 과제 중 정의서 v1 작성 비율 | 80% 이상 | 분기 말 자동 집계 |
| 프롬프트 저장율 | 운영 에이전트 중 핵심 프롬프트 GitHub 저장 비율 | 100% (운영 전 필수) | Agent ID 발급 시 체크 |
| 감사 로그 근거 포함율 | Tool Call 기록 중 "왜 이 판단을 했는가" 포함 비율 | 90% 이상 | 월간 자동 집계 |
| 실패 학습 기록 건수 | 폐기·반려 에이전트 중 원인·교훈 문서 작성 건 | 분기 1건 이상 | 분기 AX팀 수동 확인 |

과제 정의서 미작성 과제는 다음 Phase 진행을 불가로 한다.

③ 2단계 — **재사용**: 쌓인 것을 다시 꺼내 쓰는가 [반기 측정, 정량]

이전에 만든 결과물이 새 과제에 실제로 활용되는지를 측정한다.

| 지표 | 무엇을 측정하는가 | 목표 | 측정 시점 |
|------|---------------|------|---------|
| Prompt Caching 적용율 | 동일 입력 반복 구간(시스템 프롬프트·참조 문서)에 캐싱 적용 비율 | 50% 이상 | 반기 AX팀 코드 점검 |
| 이관 후 재작업율 | 이관 시 AX팀이 CREW 코드를 처음부터 다시 짠 비율 | 30% 이하 | 이관 완료 후 2주 내 기록 |
| 사례 인용 건수 | 신규 과제 정의서에서 기존 과제·프롬프트를 참조한 건수 | 반기 3건 이상 | 반기 인벤토리 검토 시 집계 |

재작업율 30% 초과 시 해당 CREW를 이관 전 완성도 기준 재교육 대상으로 분류한다.

④ 3단계 — **이전**: 사람이 바뀌어도 굴러가는가 [반기 측정, 정성]

담당자가 떠나도 업무가 끊기지 않는지를 측정한다.

| 지표 | 무엇을 측정하는가 | 평가 방법 | 측정 시점 |
|------|---------------|---------|---------|
| 신규 CREW 온보딩 기간 | 처음 합류한 CREW가 첫 과제를 제출하기까지 걸린 주 수 | 전 분기 대비 단축 여부 | 반기 HR 데이터 연계 |
| 업무 연속성 | 핵심 인력 이탈 시 에이전트로 커버 가능한 업무 비율 | AX팀장 + 현업 부서장 인터뷰 | 이탈 발생 시 즉시 |
| 에이전트 독립성 | "이 에이전트를 만든 사람 없이도 운영·수정 가능한가" 심사 | 가능(맥락 문서화 완료) / 불가(담당자에게 종속됨) | 반기 인벤토리 검토 시 |

에이전트 독립성 "불가" 판정 시 맥락 문서화 작업을 다음 분기 필수 과제로 등록한다.

⑤ 보고 및 활용 기준은 다음과 같다.

1. AX팀은 반기 운영 보고 시 1·2단계 집계, 3단계 정성 평가 결과를 AX 위원회에 보고한다.
2. 개인 사용량은 부서 단위로 익명화하여 보고하며, 개인 식별 정보를 인사 평가에 직접 연계하지 않는다.
