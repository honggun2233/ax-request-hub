## 제1장 AI CREW

AI CREW는 각 부서에서 업무 프로세스 혁신과 AI 활용을 함께 선도하고 AX팀과 소통하는 현업 담당자다.

| 역할 |
|------|
| 부서 내 현행 업무(As-Is) 진단 및 혁신 기회 발굴 |
| AI 활용 사례 발굴 및 AX팀 창구 역할 |
| 과제 정의서 v0 작성 및 제출 |
| 파일럿 단계 UAT 수행 및 현업 검증 |

### AI CREW 등급 체계

AI CREW는 역량에 따라 3단계로 구분하며, AX팀이 등급별 지원을 제공한다.

| 등급 | 명칭 | 기준 | AX팀 지원 |
|------|------|------|---------|
| **Lv.1 탐색** | AI 탐색자 | No-Code 도구 활용 가능, 과제 아이디어 발굴 단계 | 기초 교육 자료 제공, 사용 가이드 안내 |
| **Lv.2 실험** | AI 실험자 | Low-Code 프로토타입 구성 가능, 파일럿 UAT 수행 경험 보유 | AX 샌드박스 환경 제공, 1:1 기술 자문 |
| **Lv.3 개발** | AI 혁신자 | Pro-Code 개발 참여 가능, APA 또는 에이전트 구현 경험 보유 | AX팀 공동 개발, 고급 템플릿·패턴 공유, 우선 과제 배정 |

- 등급은 AX팀이 과제 참여 이력과 역량을 기반으로 부여하며 연 1회 이상 갱신한다.
- AI CREW 자원은 AX팀에 직접 문의하여 신청하며, AX팀이 배정 부서를 조율한다.

## 제2장 AI 과제 단계 (Phase 0 → Phase 6)

유형 2 이상 AI 과제는 아래 단계를 순서대로 진행한다. 단계 건너뛰기는 금지된다.

| 단계 | 담당 | 산출물 | 기준 |
|------|------|-------|------|
| **Phase 0 발굴** | AI CREW | As-Is 업무 분석, 아이디어 메모 | AI 도입 전 현행 프로세스 진단 필수. AI 없이도 개선 가능한지 먼저 검토 |
| **Phase 1 기획** | AI CREW + AX팀 | 과제 정의서 v0 | 접수 후 결과 통보: 저위험·G1 → 5영업일 / 중위험·G2 → 10영업일 / 고위험·G3 → 15영업일 |
| **Phase 2 설계** | AX팀 | 과제 정의서 v1, 설계 리뷰서 | 고위험 시 컴플라이언스 사전 검토 |
| **Phase 3 MVP 개발** | AX팀 | MVP, 테스트 결과서 | G2 이상: 개발 단계 실 데이터 사용 금지 |
| **Phase 4 심사** | AX팀 | 심사 보고서, 위험 평가서 | 자동 평가 70점 이상 → 파일럿 진입 |
| **Phase 5 파일럿** | AI CREW + AX팀 | UAT 결과, KPI | 중위험 4~6주 / 고위험 8주 |
| **Phase 6 운영** | AX팀 | Agent ID, 운영 명세서 | 위험등급별 승인 후 배포 |

## 제3장 관련 부서 협조

AX팀이 과제 파이프라인을 주관한다. 아래 단계에서 관련 부서 협조가 필요하다.

| Phase | 협조 내용 | 관련 부서 |
|-------|---------|---------|
| Phase 2 설계 | G2 인프라 가용성 확인 | AI데이터플랫폼팀 |
| Phase 4 심사 | 보안 검토 | 정보전략팀 |
| Phase 4 심사 | 고위험 컴플라이언스 검토 | 컴플라이언스 |
| Phase 6 운영 | 시스템 운영 유지보수 인수 | IT업무개발팀 |
| Phase 6 운영 | 고위험(투자·운용 실행·공시·컴플라이언스 판정) 과제 최종 승인 | **AX 위원회** |

각 부서의 세부 역할은 별도 협의를 통해 확정한다.

### AX 위원회 상정 절차

고위험 과제 중 투자·운용 실행, 공시·법정문서, 컴플라이언스 판정 업무에 해당하는 과제는 운영 승격 전 AX 위원회 승인이 필요하다.

1. AX팀장이 심사 보고서(과제 개요·위험 평가·KPI·파일럿 결과)를 작성한다.
2. 정기회의 또는 임시회의 안건으로 상정한다.
3. 위원회 의결 후 AX팀이 Agent ID를 발급하고 운영을 개시한다.

위원회 구성·임무·회의 운영 세부사항은 `운영방안_AX위원회.md`에 따른다.

## 제5장 과제 자동 평가 기준 (6차원, 100점)

| 차원 | 배점 | 기준 |
|------|------|------|
| 임팩트 | 25 | 영향 인원·빈도·전략 정합성 |
| ROI | 25 | 시간·비용 절감 및 수익 기여를 산정하여 기재. 정량화가 어려운 경우 정성적 근거와 함께 작성 |
| 기밀등급 | 15 | G1 고배점, G3 저배점 |
| 난이도 역산 | 15 | 낮은 난이도 = 고점 |
| 현업 준비도 | 10 | 데이터 가용성, AI CREW 유무 |
| 전략 정합성 | 10 | AX 로드맵 과제 연관성 |

- **70점 미만 또는 G3** → AX팀장 판단
- **68~72점 경계** → 팀장 직접 검토 (자동 처리 금지)

## 제6장 위험등급별 통제 요건

### 위험등급 결정 순서

```
1. 업무 분류 → 규정 제6조 목록 대조
2. 기밀등급 → G3 포함 시 고위험 자동 상향 / G2만이면 최소 중위험
3. 유형     → 유형 3·4이면 최소 중위험
4. 영향 범위 → 고객 자산·계약 영향이면 고위험 자동 상향
```

등급이 애매하면 상위 등급으로 분류한다.

### 고위험 필수 통제

| 항목 | 기준 |
|------|------|
| Human-in-the-loop | 담당자 + 팀장 이중 검토 후 실행 |
| 독립 검증 | 개발팀과 독립된 부서가 별도 검증 |
| 출처 강제 | 모든 AI 응답에 근거 데이터·출처 명시 |
| 감사 로그 | 입력→처리→출력 전 과정 기록, **5년 보존** |
| 사전 승인 | 유형 3·4 적용 시 AX팀장 + 팀 상위 승인 |
| Kill Switch | Circuit Breaker 구현 의무 |
| 롤백 절차 | 운영 중 장애 발생 시 이전 버전·수동 처리로 즉시 전환하는 절차를 사전 정의 |

**감사 로그 필수 필드**

| 필드 | 내용 |
|------|------|
| timestamp | UTC 기준 ISO 8601 |
| agent_id | AX팀 발급 Agent ID |
| event_type | llm_call / tool_call / human_checkpoint / error |
| input_summary | 입력 요약 (G3 원문 제외) |
| output_summary | 출력 요약 |
| tool_name | 호출한 도구명 (tool_call 시) |
| user_id | 요청자 또는 트리거 시스템 식별자 |
| decision | 사람 검토 결과 (human_checkpoint 시) |

**운영 승격 기준**

| 단계 | 기간 | 기준 | 승인 |
|------|------|------|------|
| PoC | 2주 | 기술 실현 가능성 확인 | AX팀장 |
| 파일럿 | 8주 | KPI 80% 이상 + 사고 0건 | 팀 상위 |
| 운영 승격 (일반) | — | KPI 90% 이상 + 감사 로그 완비 | 팀 상위 + 준법감시인 |
| 운영 승격 (투자·운용 실행·공시·컴플라이언스 판정 해당) | — | KPI 90% 이상 + 감사 로그 완비 | 팀 상위 + 준법감시인 + **AX 위원회 최종 승인** |

### 중위험 필수 통제

| 항목 | 기준 |
|------|------|
| 사람 검토 후 확정 | AI 산출물은 초안. 담당자 검토 후 최종 확정 |
| 출처 명시 | 사실 주장 시 근거 출처 포함 |
| 분기별 KPI 점검 | 정확도·사용률·오류율 점검 |
| 과제 등록 의무 | 유형 2 이상 → AX팀 과제 등록 후 운영 |

**운영 승격 기준**

| 단계 | 기간 | 기준 | 승인 |
|------|------|------|------|
| PoC | 2주 | 기술 실현 가능성 확인 | AX팀장 |
| 파일럿 | 4~6주 | KPI 60% 이상 | AX팀장 + 현업 부서장 |
| 운영 승격 | — | KPI 80% 이상 + 사고 0건 | 팀 상위 |

### 위험등급 재평가 기준

아래 상황 발생 시 즉시 재평가한다.
- 적용 업무 범위가 최초 등록보다 확대된 경우
- 더 높은 기밀등급의 데이터를 새로 처리하게 된 경우
- 관련 법령·감독지침이 개정된 경우
- 연간 정기 재평가 (매년 1월)

## 제7장 에이전트 라이프사이클 (유형 3·4)

에이전트 라이프사이클은 **생성 라이프사이클**(Phase Gate 0→6)과 **관리 라이프사이클**(상태 머신)로 구분한다. 두 라이프사이클은 Phase 5 파일럿 진입 시점에 교차한다.

### 7-1 사전 설계 체크 (운영 전 AX팀과 확인 필수)

| 항목 | 확인 사항 |
|------|---------|
| 목표 | 에이전트가 달성하는 구체적인 결과물은 무엇인가. 목표가 두 개 이상이면 에이전트를 분리한다. |
| 범위 | 절대 하면 안 되는 것 목록을 시스템 프롬프트에 명시했는가 |
| 도구 | 목표에 필요한 최소한의 도구만 허용했는가 |
| Human Checkpoint | 고위험 결과 전 사람 승인 포인트가 있는가 |
| Kill Switch | 즉시 중단 조건과 중단 후 행동이 정의되어 있는가 |
| 감사 추적 | 모든 Tool Call과 판단 근거를 기록하는가 |
| 실패 모드 | 실패 시 행동(알림·롤백·중단)이 정의되어 있는가 |
| 평가 KPI 사전 합의 | 과제 정의서 v1에 측정 가능한 KPI 목표값이 기재되었는가 (제14장 보상 평가 연계) |

### 7-2 Agent ID 체계

```
형식: AX-{YYYY}-{유형코드}-{순번}
유형코드: AGT (단독 에이전트) / MAS (멀티 에이전트 시스템)
예: AX-2026-AGT-001
멀티 에이전트 서브: AX-2026-MAS-001-SUB-A

임시 ID (파일럿 전용): AX-DEV-{YYYY}-{순번}
예: AX-DEV-2026-001 → 운영 전환 시 정식 ID로 교체
```

**Agent ID 발급 범위 (Phase·데이터등급 기준)**

| 상황 | ID 유형 | 발급 주체 | 데이터 접근 |
|------|--------|---------|-----------|
| G1 개인 실험 (Phase 0~2) | 없음 | — | G1만 (샌드박스 권장) |
| G1 팀 공유 PoC (Phase 3~4) | 없음 | AX팀 인식·등록만 | G1, 샘플 데이터 |
| Phase 5 파일럿 (G1/G2) | **AX-DEV- (임시)** | AX팀 | G1/G2, 제한 실데이터 |
| Phase 6 운영 | **AX-YYYY-AGT-XXX (정식)** | AX팀 | 설계 기준 전체 접근 |

### 7-3 생성 라이프사이클 (Phase 0 → 6)

| Phase | 명칭 | ID 상태 | 에이전트 상태 | 데이터 접근 | AX팀 역할 | 데이터플랫폼팀 역할 |
|-------|------|--------|-------------|-----------|---------|----------------|
| 0 | 발굴 | 없음 | — | G1만 | 존재 인식 | — |
| 1 | 기획 | 없음 | — | G1만 | 과제 등록 | — |
| 2 | 설계 | 없음 | — | G1, 샘플 | 기술 검토·설계 지원 | 샘플 데이터 제공 |
| 3 | MVP | 없음 | 개발 중 | G1, 샘플 | AX팀 인식·등록 | 샘플 데이터 제공 |
| 4 | 심사 | 없음 | 심사 중 | G1, 샘플 | 심사 보고서 작성 | — |
| 5 | 파일럿 | AX-DEV- (임시) | 🟡 등록신청 | G1/G2, 제한 실데이터 | 임시 ID·파일럿 운영 | 제한 실데이터·SLA |
| 6 | 운영 | AX-YYYY-AGT-XXX (정식) | 🟢 Active | 설계 기준 전체 | 정식 ID·모니터링 활성화 | 전체 접근권한 갱신 |

### 7-4 관리 라이프사이클 (상태 머신)

| 상태 전환 | 조건 | AX팀 역할 | 데이터플랫폼팀 역할 |
|---------|------|---------|----------------|
| **→ 🟡 등록신청** | Phase 5 파일럿 진입 승인 | 임시 ID 발급, 인벤토리 신규 등록 | 제한 실데이터 접근 권한 부여 |
| **🟡 → 🟢 Active** | Phase 6 운영 승격 | 정식 ID 교체, KPI 모니터링 활성화 | 전체 접근권한 갱신 |
| **🟢 → 🔵 Suspended** | 사고·점검·업무 변화 | 원인 분석, 접근권한 일시 차단 | 데이터 접근 일시 차단 |
| **🔵 → 🟢 Active** | 원인 해소 후 복구 승인 | 복구 검토, 재활성화 | 접근권한 복구 |
| **\* → 🔴 Retired** | 폐기 기준 충족 | ID 비활성화, 인벤토리 폐기 등록 | 접근권한 전체 회수 |

**폐기 기준** (하나라도 해당 시 폐기):
- KPI 60% 미달 3개월 연속
- 데이터 유출·보안 사고 발생
- 12개월 연속 미사용
- 담당 업무 소멸

폐기 후 감사 로그는 보존 기간 유지. Agent ID 재사용 금지.

### 7-5 프롬프트 버전 관리

프롬프트는 코드와 동일하게 관리한다.

- 시스템 프롬프트는 코드 저장소에 포함하여 Git으로 버전 관리한다
- 프롬프트 변경 시 코드 변경과 동일한 리뷰 절차(PR·승인)를 거친다
- 변경 이력(변경 이유, 변경 전·후, 테스트 결과)을 커밋 메시지에 기록한다
- 운영 중 프롬프트 핫픽스도 동일한 절차를 적용하며, 사후 즉시 기록한다

### 7-6 에이전트 인벤토리

에이전트 상태 변경·ID 발급 이벤트 발생 시 자동 업데이트. 반기 1회 수동 전수 확인(누락·좀비 에이전트 점검).

## 제8장 자원·비용 관리

### 예산·비용 편성

AI 과제 관련 예산 편성·승인·집행 기준은 별도 사규에 따른다. AX팀은 과제별 예상 비용을 과제 정의서 v1에 명시하고 해당 사규 절차에 따라 예산을 신청한다.

### API 키 관리 원칙

| 용도 | 발급 방법 | 조건 |
|------|---------|------|
| **G1 개인 실험** (Phase 0~2) | CREW가 직접 발급 가능 | 발급 후 AX팀 키 목록에 등록만 |
| **G1 팀 공유·파일럿 이상** | AX팀 신청 → 과제별 키 발급 | 과제 등록 선행 필수 |
| **G2 이상 모든 용도** | AX팀 신청 필수 | G2 접근 사전 AX팀 승인 후 발급 |

공통 원칙:
- 코드 하드코딩 금지 → `.env` 파일 저장, `.gitignore` 필수
- `.env` GitHub 업로드 금지 → 발견 즉시 키 무효화
- 공유 폴더·이메일·메신저로 키 전달 금지

### 토큰 사용량 관리

AX팀은 과제별 토큰 사용량을 추적·통제할 책임을 진다.

**할당 원칙**

| 단계 | 한도 | 승인 |
|------|------|------|
| 개발·테스트 | AX팀이 과제별 상한 책정 | AX팀 |
| 파일럿 | 기획 단계 예상 사용량 기준 책정 | AX팀장 |
| 운영 | 파일럿 실측치 기반 월 예산 확정 | 팀 상위 |

**모니터링**

- 과제마다 API 키를 분리 발급하여 과제별 사용량을 독립 추적한다
- **AX팀 수동 확인은 최소화**: 자동 알림이 한도 임박(80%) 또는 이상 급증(전주 대비 200% 초과) 시 AX팀과 담당자에게 자동 통보. AX팀은 알림 수신 시에만 개입한다
- 한도 초과 시 자동 정지 또는 알림 후 담당자 판단 중 과제 설계 단계에서 결정 (G1·저위험은 알림+담당자 판단, G2 이상·고위험은 자동 정지 권장)

**효율화 원칙**

- 동일 입력이 반복되는 구간에는 Prompt Caching을 우선 적용한다
- 분류·라우팅처럼 정형화된 작업은 경량 모델을 쓴다 (아래 모델 선택 기준 참조)
- 과제 기획 시 월 예상 토큰 사용량을 과제 정의서 v1에 명시한다

### 모델 선택 기준

| 용도 | 모델 |
|------|------|
| 일반 업무 | claude-sonnet-4-6 |
| 대량 분류·라우팅 | claude-haiku-4-5 |
| 복잡 추론 (필요 시만) | claude-opus-4-8 |

비용 대비 품질 검증 없이 최상위 모델을 기본으로 사용하는 것은 금지한다.

### 암묵지 데이터화 성숙도 평가 (직원·조직 AI 활용 평가)

AI Native 조직의 핵심 지표는 "얼마나 썼는가"가 아니라 **"쓴 만큼 조직 지식이 축적됐는가"** 이다.  
아래 3개 차원으로 평가한다. 차원 1은 분기, 차원 2·3은 반기 측정을 원칙으로 한다.

#### 차원 1 — 지식 포착 (암묵지 → 형식지 전환) [정량]

| 지표 | 측정 방법 | 정량 목표 | 측정 시점 |
|------|---------|---------|---------|
| 과제 정의서 완료율 | 등록 과제 중 정의서 v1 작성 비율 | ≥ 80% | 분기 말 자동 집계 |
| 프롬프트 문서화율 | 운영 에이전트 중 핵심 프롬프트 GitHub 저장 비율 | 100% (운영 전 의무) | Agent ID 발급 시 체크 |
| 의사결정 감사로그 충족율 | Tool Call 기록 중 판단 근거 포함 비율 | ≥ 90% | 월간 자동 집계 |
| 실패 리뷰 작성 건수 | 폐기·반려 에이전트 중 학습 노트 작성 건 | 분기 1건 이상 | 분기 AX팀 수동 확인 |

> 미달 시: AX팀이 해당 부서에 보완 요청. 과제 정의서 미작성 과제는 다음 Phase 진행 불가.

#### 차원 2 — 활용·재사용 (쌓인 context가 실제로 쓰이는가) [정량]

| 지표 | 측정 방법 | 정량 목표 | 측정 시점 |
|------|---------|---------|---------|
| Prompt Caching 적용률 | 동일 입력 반복 구간에 캐싱 적용 비율 | ≥ 50% | 반기 AX팀 코드 점검 |
| 이관 후 AX팀 재작업률 | 이관 시 AX팀 코드 수정 비율 | ≤ 30% | 이관 완료 후 2주 내 기록 |
| 과거 과제 참조 빈도 | 신규 과제 정의서에서 기존 사례 인용 건수 | 반기 3건 이상 | 반기 인벤토리 검토 시 집계 |

> 재작업률 30% 초과 시: CREW 이관 전 완성도 기준(제19조) 재교육 대상으로 분류.

#### 차원 3 — 조직 역량 (사람이 바뀌어도 유지되는가) [정성]

| 지표 | 측정 방법 | 평가 방법 | 측정 시점 |
|------|---------|---------|---------|
| 신규 CREW 온보딩 기간 | 첫 과제 제출까지 걸린 주 수 | 전 분기 대비 단축 여부 | 반기 HR 데이터 연계 |
| 핵심 인력 이탈 후 업무 연속성 | 이탈 발생 시 에이전트로 커버 가능한 업무 비율 | AX팀장 + 현업 부서장 인터뷰 | 이탈 발생 시 즉시 |
| 에이전트 자립도 | "이 에이전트 없이 같은 결과 가능한가" 심사 | Yes(context 외부화됨) / No(에이전트에 갇힘) | 반기 인벤토리 검토 시 |

> 에이전트 자립도 No 판정: context 외재화 작업을 다음 분기 필수 과제로 등록.

#### 보고 및 활용

- AX팀은 반기 운영 보고 시 차원 1·2 집계, 차원 3 정성 평가 결과를 AX 위원회에 보고한다
- 개인 사용량은 부서 단위로 익명화하여 보고하며, 개인 식별 정보를 인사 평가에 직접 연계하지 않는다
- AI CREW 등급 심사(Lv.1→2, 2→3 승급) 시 본인 동의 하에 차원 1 지표를 참조할 수 있다
- 차원 1 목표 2개 이상 미달 부서는 다음 반기 과제 등록 상한을 1건으로 제한한다

## 제9장 변화관리 및 사내 커뮤니케이션

### 기본 입장

AI는 담당자의 판단을 보조하는 도구다. AI 도입은 업무를 대체하는 것이 아니라, 반복·단순 업무를 줄여 담당자가 더 높은 가치 업무에 집중하도록 지원하기 위한 것이다. AX팀은 이 메시지를 일관되게 전달할 책임을 진다.

### AI CREW 모집 및 온보딩

- AI CREW 자원은 AX팀에 직접 문의하여 신청한다
- 신청 후 AX팀이 부서별 배정을 조율하고 초기 교육을 제공한다
- 처음 시작하는 AI CREW는 Lv.1(탐색) 등급부터 시작하며, Claude.ai·ChatGPT 직접 활용(유형 1, G1 데이터)으로 진입한다
- AX팀은 Lv.1 대상 "첫 번째 과제 30분 시작 가이드"를 제공한다

### 파일럿 성과 공유

- 파일럿이 완료된 과제 중 공유 가능한 결과는 AX팀이 사내 채널에 공유한다
- 형식: 어떤 업무에 적용했는지, 어떤 결과가 나왔는지, 어떻게 쓸 수 있는지 (수치 포함)
- 실패한 PoC도 학습 공유 대상이다. 왜 안 됐는지를 공유하는 것도 혁신의 일부다

### 팀장 역할 안내

팀장은 직원의 AI CREW 자원을 승인하고 파일럿 참여를 지원하는 역할을 한다.

| 상황 | 팀장 역할 |
|------|---------|
| AI CREW 자원 시 | 부서 내 적합자 추천 또는 승인 |
| 파일럿 진행 중 | 현업 데이터 제공, 일정 조율 지원 |
| 운영 승격 심사 | 현업 부서장 승인 참여 |

### 얼리어답터 인정

- AX팀은 분기별로 과제 기여가 높은 AI CREW를 AX/PI센터장에게 보고한다
- 인정 방식은 AX/PI센터 내부 운영 방식에 따른다

## 제10장 AI CREW 개발·고도화 파이프라인

### 제18조 AI CREW 역할 정의

AI CREW는 현업 부서에서 AI 과제의 초기 탐색과 프로토타입을 담당하는 내부 참여자다.

| 등급 | 역할 | 기대 산출물 |
|------|------|-----------|
| Lv.1 | No-Code 탐색 | AI 활용 아이디어, 도입 제안서 |
| Lv.2 | Low-Code 실험 | 작동 프로토타입 (AX 샌드박스 활용) |
| Lv.3 | Pro-Code 개발 | API 연동·에이전트 초안 (AX팀 협업) |

### 제19조 AX팀 이관 기준 및 AX팀 개발 역할

AI CREW는 PoC·프로토타입 수준까지 개발하고, 이관 기준을 충족하면 AX팀에 인수한다. **이관 후 고도화 개발은 AX 엔지니어가 주도한다.** AX팀은 판단·승인만 하는 팀이 아니라 고도화 개발과 운영의 직접 담당 주체다.

#### 이관 판정 (3단계)

| 단계 | 기준 | 판정 방법 |
|------|------|---------|
| 이관 검토 | 프로토타입이 2주 이상 현업에서 반복 사용됨 | AX팀 분기 CREW 리뷰 (초기 등록 후 첫 6개월은 월간) |
| 이관 결정 | 위험등급 中 이상 **또는** 타 부서 연동 필요 | 자동 평가 점수 ≥ 70 |
| 이관 완료 | AX팀이 Agent ID 발급 + 모니터링 설정 완료 | Phase 5 운영 등록 |

#### CREW 이관 전 코드 완성도 기준 (AX팀 재작업 최소화 핵심)

> AX팀 과중을 줄이는 가장 효과적인 방법은 이관 시점에 완성도 높은 코드를 받는 것이다. 아래 5가지를 충족하지 않으면 이관을 거부할 수 있다.

| # | 완성도 요건 | 미충족 시 |
|---|-----------|---------|
| ① | 핵심 기능 로컬 시연 가능 (스크린샷 또는 실시간 데모) | 이관 반려 |
| ② | 입출력 명세 문서화 (예: 입력 포맷·출력 포맷 각 1장 이내) | 이관 반려 |
| ③ | 핵심 코드 GitHub 저장 + README 최소 포함 | 이관 반려 |
| ④ | 기밀 데이터 포함 여부 명시 및 .env 분리 | 이관 반려 |
| ⑤ | 예상 사용자 수·실행 빈도 추정치 제출 | 이관 보류 (AX팀 추정 가능 시 진행) |

이관 전까지 AI CREW는 G1 범위 내에서 자율 운용하며, 이관 후에는 **AX팀이 오너십과 개발 주도권을 갖는다.**

### 제20조 AI CREW 개발 지표 (6종)

AI CREW 활동은 아래 6개 지표로 분기별 측정한다.

| # | 지표 | 정의 | 목표 |
|---|------|------|------|
| ① | 과제 등록 건수 | 분기 중 과제 정의서 제출 건 | 부서당 2건 이상 |
| ② | 프로토타입 완성률 | 등록 과제 중 작동 프로토타입 존재 비율 | ≥ 60% |
| ③ | 이관 전환율 | 프로토타입 중 AX팀 이관 비율 | ≥ 30% |
| ④ | 자동 평가 점수 평균 | 제출 과제의 6차원 평가 평균 | ≥ 65점 |
| ⑤ | 현업 활용 지속성 | 이관 후 6개월 이상 운영 유지 비율 | ≥ 70% |
| ⑥ | 운영 장애 발생률 | 에이전트 비정상 종료 건수 / 전체 운영일 | ≤ 2% |

### 제21조 기획 단계 AX 기획자 역할

Phase 1 (기획) 단계에서 AX 기획자는 다음 역할을 수행한다.

1. **과제 정의서 작성 지원**: AI CREW가 제출한 아이디어를 구조화된 과제 정의서(v0)로 변환
2. **자동 평가 해석**: 6차원 평가 결과를 현업이 이해할 수 있도록 해석·설명
3. **우선순위 조율**: 복수 과제 경쟁 시 기술 가능성·비즈니스 임팩트 기준으로 순서 조율
4. **이해관계자 정렬**: 현업 부서·AX 엔지니어·컴플라이언스 간 요구사항 갭 식별
5. **Phase Gate 관리**: 각 Phase 전환 조건 충족 여부 점검 및 진입 승인

AX 기획자는 과제 정의서 v1 완성 전까지 AI CREW와 최소 **1회** 리뷰를 수행해야 한다. (Lv.2 이상 CREW는 셀프 리뷰 인정, 단 AX팀 최종 확인 필수)

### 제22조 AX 엔지니어 개발 기준

Phase 3 (MVP 개발) 이후 AX 엔지니어는 다음 기준을 반드시 준수한다.

1. **Agent ID 선발급**: 코드 작성 전 AX팀에서 Agent ID를 발급받고 코드에 하드코딩
2. **감사 로그 필수**: 모든 LLM 호출·도구 실행은 `log_audit()` 함수를 통해 기록
3. **Kill Switch 구현**: 유형 3·4는 Circuit Breaker 패턴 필수 (가이드라인 제4장 참고)
4. **최소 권한 원칙**: 도구는 업무에 필요한 것만 정의. 추가 권한은 AX팀 검토 후 부여
5. **합성 데이터 선행 검증**: G2 이상 실 데이터 사용 전 합성 데이터로 기능 검증 완료
6. **PR·코드리뷰 의무**: AX팀이 개발 주체이므로 운영 배포 전 AX팀 내 최소 1인 코드리뷰 통과 필수. Lv.3 CREW가 공동 개발에 참여한 경우 CREW를 추가 리뷰어로 포함할 수 있으나 AX팀 리뷰를 대체하지 않는다. 리뷰 효율화는 표준 리뷰 체크리스트(이관 완성도·보안·KPI 측정 가능성 3항목)를 활용한다.
7. **운영 인수 문서**: 배포 시 운영 매뉴얼(에이전트 설명, 장애 대응, 롤백 절차) 작성

## 제11장 배포 환경 결정 기준

### 제23조 배포 환경 유형

AI 과제의 배포 환경은 기밀등급·운용 특성·인프라 조건에 따라 세 가지 중 하나로 결정한다.

| 환경 | 적용 대상 | 대표 서비스 |
|------|---------|-----------|
| GPT Enterprise | G1, 사내 정형 문서 작업·생산성 도구 | Microsoft Copilot, ChatGPT Enterprise |
| AWS Landing Zone | G1~G2, 대용량 처리·외부 연동·스케일링 필요 | Bedrock(Claude), SageMaker |
| 온프레미스 (사내) | G2·G3, 기밀 운용 데이터·포지션 정보 포함 | 사내 서버, OpenClaw, 내부 API |

### 제24조 배포 환경 결정 트리

```
데이터에 G3(고객 PI·미공개 운용 포지션)이 포함되는가?
├─ YES → 온프레미스 (외부 전송 절대 금지)
└─ NO  → G2 데이터가 포함되는가?
          ├─ YES → 온프레미스 또는 AWS Bedrock (사내 VPC 내)
          └─ NO  → 대용량 처리 또는 외부 API 연동이 필요한가?
                    ├─ YES → AWS Landing Zone
                    └─ NO  → 생산성·협업 도구 성격인가?
                               ├─ YES → GPT Enterprise
                               └─ NO  → AWS Landing Zone 또는 온프레미스
```

**추가 조건**

- 실시간 운용 의사결정(주문·리밸런싱 판단)이 포함되면 온프레미스 우선
- 외부 규제 신고(공시·보고서 제출) 데이터가 포함되면 컴플라이언스팀 사전 승인 필요
- AWS Landing Zone 사용 시 AI데이터플랫폼팀과 VPC 피어링·IAM 정책 협의 필수

## 제12장 데이터플랫폼팀 연계

### 제25조 협업 원칙

AI 과제가 데이터플랫폼팀 소관 데이터 소스(DW, Mart, 실시간 피드)를 사용할 경우, 아래 원칙을 따른다.

1. **선협의 원칙**: 데이터 소스 결정 전 데이터플랫폼팀과 가용성·SLA·기밀등급 확인
2. **계약 기반 접근**: 비공식 직접 연결 금지. 데이터 요청서 → 검토 → 접근 권한 부여 순서 준수
3. **CDO 카탈로그 등록**: 사용하는 데이터 소스는 CDO 데이터 카탈로그에 등록 후 사용
4. **SLA 준수**: 데이터 신선도(T+1, T+0 등) 요건은 과제 정의서에 명시, 데이터플랫폼팀 확인 필요

### 제26조 데이터 요청 표준

AX팀이 데이터플랫폼팀에 데이터 접근을 요청할 때 다음 정보를 제공한다.

| 항목 | 내용 |
|------|------|
| 과제명 / Agent ID | AX 과제명, 발급된 Agent ID |
| 요청 데이터 | 데이터셋명, 테이블/컬럼 범위 |
| 사용 목적 | 어떤 AI 기능에 사용하는지 1~2줄 |
| 기밀등급 | 요청 데이터의 등급 (G1/G2/G3) |
| 접근 방식 | API 호출 / 배치 추출 / 스트리밍 |
| 갱신 주기 | 실시간 / 일 1회 / 주기 없음 |
| 사용 기간 | 프로젝트 종료일 또는 상시 |

### 제27조 데이터 플로우 문서화 기준

데이터플랫폼팀 연계가 포함된 과제는 아래 흐름을 과제 정의서에 다이어그램으로 포함한다.

```
[데이터 원천]
  └─ 데이터플랫폼팀 DW/Mart
       └─ (API 또는 배치 추출)
            └─ AX 과제 수신 레이어 (기밀등급 경계 표시)
                 └─ AI 모델/에이전트 처리
                      └─ 산출물 (결과 저장·전달 방식)
                           └─ (G2 이상이면 온프레미스 내부에서만 유통)
```

**문서화 필수 항목**

- 데이터 흐름의 각 단계에서 기밀등급 명시
- G2 경계를 넘는 지점 표시 (외부 전송 금지 경계)
- 비정상 데이터 수신 시 처리 방법 (폴백·알림·중단)
- 데이터플랫폼팀 SLA 위반 시 에이전트 동작 정의

## 제14장 우수 에이전트 인정 및 보상

> **목적**: 잘 만들어진 에이전트와 이를 개발한 AI CREW를 공식적으로 인정하고 보상함으로써, 자발적 혁신 동력을 유지하고 사내 AI 문화를 확산시킨다.

### 우수 에이전트 선정 기준

**핵심 원칙**: 과제 정의서 v1에 목표값을 사전 합의한 지표만 유효한 평가 기준으로 인정한다. 사전 합의가 없으면 해당 기준은 0점으로 처리한다.

| 기준 | 배점 | 측정 방법 | 데이터 소스 | 사전 합의 여부 |
|------|------|---------|-----------|------------|
| **KPI 달성률** | 30 | 과제 정의서 v1 목표 대비 실적 달성 % | 감사 로그 자동 집계 | **과제 정의서 v1 필수** |
| **ROI 실현** | 25 | 절감 시간·비용 합산 (연환산) | 현업 부서장 확인 서명 | **과제 정의서 v1 필수** |
| **지속 활용** | 20 | 운영 90일 이상 + 월 활용 빈도 유지 | 인벤토리 자동 집계 | 불필요 |
| **문서화** | 15 | 프롬프트·운영 매뉴얼·감사로그 완비 여부 | AX팀 검토 | 불필요 |
| **혁신성** | 10 | 신규 업무 영역 최초 적용 또는 타 부서 전파 여부 | AX팀 수동 평가 | 불필요 |

### 보상 등급 및 지원

| 등급 | 기준 | 보상 내용 |
|------|------|---------|
| **우수 에이전트** | 80~89점 | AX팀장 포상 추천, 다음 과제 우선 배정, 사내 채널 공유 |
| **탁월 에이전트 (AX Excellence)** | 90점 이상 | AX/PI센터장 표창, 성과 인센티브 연계 (HR·경영기획 협의), 전사 사례 발표 |

### 심사 운영

- **심사 주기**: 분기 1회 (1·4·7·10월 말)
- **심사 대상**: 🟢 Active 90일 이상 유지한 에이전트 (🟡 등록신청 또는 🔵 Suspended 상태 제외, 복구 후 다음 분기 자동 편입)
- **자동 집계 트랙**: KPI 달성률·지속 활용·문서화 → AX팀 인벤토리·감사로그 자동 집계
- **AX팀 수동 트랙**: ROI 실현(부서장 서명 수집) + 혁신성(AX팀 수동 평가)
- **이의 신청**: 결과 발표 후 5영업일 이내 AX팀에 이의 신청 가능

### 실패 리뷰 제도

폐기(🔴 Retired)된 에이전트도 학습 공유 대상이다. AX팀은 분기 1건 이상 실패 리뷰 노트를 작성하여 사내 공유한다. 실패 이유를 공유하는 것도 AI Native 문화의 일부다.
